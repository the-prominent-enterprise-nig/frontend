# Scenario 53 — Manual RR for Non-Supplier Sources, Under Accounting — Gap Analysis & Implementation Plan

**Source**: developer request, 2026-09-19 (chat, not yet a written client brief). Directives given directly, in order, including a mid-session correction of the design:

1. The manual-RR creation surface should live under **Accounting**, not Inventory.
2. Stop assuming the source is a registered Supplier — for the non-supplier case, it should just be a **free-text field**.
3. Stop assuming what's received is a catalog **Item** at all — no item search. A manual RR exists precisely for receiving _anything_, not just a recognized, serial-tracked SKU. This is the actual reason this feature exists, separate from the supplier question.
4. **Correction, same session**: a manual RR should still behave exactly like a normal RR once submitted — GL posting, AP Bill drafting, and payment all included. "Manual" describes how it originates (no PO/transfer/count context, needs a second approver), not a cut-down version of what happens after. If the typed supplier/item doesn't already exist as a real record, the system creates one — it doesn't skip the machinery that depends on one existing.

## What already exists (verified against live code, 2026-09-19)

- **Inventory's Manual RR (Scenario 29 RR-05, GL-enabled by Scenario 36 Gap 3)** — `ManualReceivingReport` model, `manual-receiving-report.service.ts`, `manual-receiving-report.controller.ts`. Originates a serial with no PO/transfer/count context: `submit()` → `pending`, a **second, distinct** user must `approve()` (self-approval blocked in the service layer), a single permission `inventory:manual-rr:create` gates submit/approve/reject/read alike, seeded to the Business Owner role only. If `unitCost` is given, `submit()` requires `supplierId` and validates it against a real `Supplier` row (`manual-receiving-report.service.ts:136-148`); `approve()` then posts `Dr Inventory / Cr AP Payable / Cr WHT` and best-effort scaffolds a DRAFT `APBill` against that supplier (`:220-372`).
- **`itemId` is also a hard requirement today, and it's not just any item.** `submit()` requires a real, existing `Item` row and rejects it outright if the item isn't serial-tracked (`:103-112`) — the whole feature is built around originating one serial number for one known catalog SKU. The frontend enforces this with a live catalog search (`ItemSearchCombobox`, borrowed from the Purchase Requests screen) before the rest of the form even unlocks. There is no way today to log a receipt for something that isn't already a serial-tracked line in the item catalog.
- **Its UI is currently unreachable.** Scenario 50 pulled the "Manual RR" tab out of `CountingHub.tsx` because it read as a second, competing "create a receipt" path next to Receive Stock — the tab was its only entry point (`manual-receiving-reports/` has no `page.tsx`). Components/hooks/actions/backend are all intact (`CreateManualRrModal.tsx`, `ManualRrList.tsx`, `ManualRrDetailView.tsx`, `useManualReceivingReports.ts`), just orphaned.
- **Accounting already has a real, reachable Receiving Reports page** — `/accounting/receiving-reports` (Scenario 36 Gap 11, added because the Accountant role holds zero `inventory:*` permissions and had no way to browse RRs at all). `ReceivingReportsList.tsx` lists every RR, matched or not, with GL-posted status and matched-bill status; backed by `GET /reports/receiving-reports`, gated by `accounting:financial_report:read`. **It is view-only today — no create action exists there.**
- **Every existing create-a-receipt path already assumes a registered Supplier.** The plain, PO-less `ReceiveStockDto` (`stock.dto.ts:246-252`) also takes `supplierId` as a real Supplier-table reference, "required when no line is linked to a PO." Nothing in this codebase today lets someone record a costed receipt from a source that isn't already a row in `Supplier`.
- **`APBill.supplierId` is a required, non-null FK** (`schema.prisma:1295`, collapsed from a separate optional Vendor/Supplier pair in Scenario 33) — an `APBill` cannot exist without a real `Supplier` row behind it.
- **`SerialNumber.itemId` and `StockLedger.itemId` are both required, non-null FKs** (`schema.prisma:5350`, `:5070`) — a serial or a stock movement cannot exist without a real `Item` row behind it.
- **The GL posting for the cost only ever touches one control account**, `MAPPING_KEYS.AP_PAYABLE` (`posting.service.ts`) — no per-supplier GL account by default (a supplier can carry a specific payable-account override, but the fallback is always the shared control account).

These last three points are why the first draft of this plan proposed a stripped-down "document only, no AP Bill, no stock movement" path for the non-supplier/non-catalog case. **That draft is superseded** — see Directive 4 above. The actual fix is to resolve a real `Supplier`/`Item` row at submit time no matter what was typed, not to work around the missing row.

- **A real, previously-unnoticed gap, found 2026-09-19 while checking "does it behave exactly like a normal RR": Manual Receiving Report posts no VAT at all.** Every other receiving path resolves Input VAT: `stock.service.ts`'s `receiveStock()` treats the caller's unit cost as VAT-inclusive by default (the PO-linked frontend, `ReceiveAgainstPoModal.tsx:353`, always sends `vatTreatment: 'inclusive'`), resolves whether the supplier charges VAT at all off `supplier.defaultInputVat` (`stock.service.ts:973`) at a flat 12% (`FLAT_VAT_RATE_PERCENT`), splits the gross into net cost + Input VAT (`:984-1019`), and posts `Dr Inventory (net) / Dr Input VAT / Cr AP Payable (net + VAT − withheld) / Cr WHT Payable` (`:1361-1394`). **`ManualReceivingReport.approve()` has none of this** — confirmed by a full-file grep, zero references to `MAPPING_KEYS.INPUT_VAT` anywhere in `manual-receiving-report.service.ts` or its DTO. It treats the entered `unitCost` as a bare net figure and posts `Dr Inventory (unitCost, full) / Cr AP / Cr WHT` with no VAT component whatsoever. Scenario 36 Part 6's own claim that "Manual Receiving Report now posts the same GL entry normal receiving does" is **not actually true on the VAT side** — it only ever matched normal receiving's withholding/AP mechanics, never its VAT mechanics.
- **Withholding is also a lesser experience today, not just missing VAT.** Both flows fall back to `supplier.defaultWithholding` the same way, but `receiveStock()` also accepts a typed `dto.withheldAmount` override — the actual amount off the supplier's BIR 2307 — while `CreateManualReceivingReportDto` has no such override field at all, only ever the flat computed 1%. On the frontend, `ReceiveStockModal.tsx` shows an editable **Withholding** select plus a read-only **computed Withheld Amount** right in the header (`:513-545`, before the Unit Cost column). `CreateManualRrModal.tsx` shows neither — withholding is entirely invisible on the form today, resolved silently server-side.

## The gap

1. There is no way to originate a manual receiving report from within Accounting — the only working create surface lives in Inventory, and even that one is currently unreachable from the UI.
2. There is no way to record a receipt when the source **isn't already a registered Supplier**, or what's received **isn't already a catalog Item** — both existing create-a-receipt paths require picking an existing row via search, with no way to originate one inline.
3. **Manual RR doesn't actually match normal receiving's financial treatment**, which Directive 4 requires it to. Two concrete misses: (a) no Input VAT is ever computed or posted, even when the supplier charges VAT; (b) withholding has no visible field or computed-amount display on the form, and no typed-override capability, unlike `ReceiveStockModal.tsx`.

## Design

### Data model — no schema change to the report itself

`ManualReceivingReport.supplierId` and `.itemId` stay exactly as they are today: real, required-when-costed FKs. There is no new `sourceName`/`description` free-text column. The only new piece of logic is **find-or-create**, applied at `submit()` time:

- **Source** (labeled "Source" on the form, backed by `Supplier`): the frontend combobox searches existing `Supplier` rows by name as today, but now also offers "Create '<typed text>' as a new source" when there's no exact match. Picking that (or the backend receiving a name with no matching id) creates a minimal `Supplier` row — name = typed text, an auto-generated code, `defaultWithholding: none` — and `submit()` proceeds with its real id exactly as if it had always existed.
- **Item**: same pattern against `Item`. A newly-created item is `isSerialTracked: true` (required, since the form still always collects one physical serial number) with an auto-generated `sku`, no category/price set yet.

### `approve()` and GL posting — unchanged from today's RR-05, plus a real VAT/WHT parity fix

Because `supplierId` and `itemId` are always resolved, real rows by the time `submit()` finishes, `approve()` needs **no branching logic at all** for the find-or-create piece. It is the same path as today: originate the `SerialNumber`, write `StockLedger`/`StockCostLayer`, and best-effort draft the `APBill` against the supplier — brand-new or pre-existing, indistinguishable to this code. That drafted bill is then payable through the normal AP Bills/Payments screens exactly like any other receipt's bill. "Payment" was never a separate thing to add — it falls out for free once both fields can resolve to a real row instead of only ever being searched for one.

**The GL posting itself, however, is not yet "the same path as today" and needs an actual fix, not just a relocation** — this was found while checking Directive 4 (act exactly like a normal RR), not part of the original ask:

- **VAT — a dropdown, not a hardcoded assumption (developer, 2026-09-19).** A simple **VAT Treatment** select: **Inclusive** / **Exclusive** (no third "exempt" option in the UI — a supplier that doesn't charge VAT already yields ₱0 VAT either way, same gating `receiveStock()` already applies off `supplier.defaultInputVat`, `stock.service.ts:994-1003`). Default to Inclusive, since that's what a physical receipt/invoice total almost always is.
- **The exact calculation, spelled out** (mirrors `receiveStock()`'s existing formula, `stock.service.ts:984-1019`, just letting the user pick the treatment instead of it always being forced to `inclusive`):
  - **If Inclusive**: the typed Unit Cost is the gross, tax-inclusive figure. `Net Cost = Unit Cost ÷ 1.12`. `Input VAT = Unit Cost − Net Cost`.
  - **If Exclusive**: the typed Unit Cost is already net. `Net Cost = Unit Cost` (as typed). `Input VAT = Unit Cost × 12%`.
  - **Withholding is separate from the VAT toggle, not baked into the same figure** — computed on the VAT-**exclusive** Net Cost either way, exactly like `receiveStock()` does today: `Withheld Amount = Net Cost × 1%` (if withholding applies), or a typed override amount off the actual BIR 2307.
  - **AP Payable** (what the drafted AP Bill actually carries) `= Net Cost + Input VAT − Withheld Amount`.
  - **GL entry**: `Dr Inventory (Net Cost) / Dr Input VAT (Input VAT, if > 0) / Cr AP Payable (Net Cost + Input VAT − Withheld Amount) / Cr Withholding Payable (Withheld Amount, if > 0)`.
- This replaces today's posting, which treats the whole typed `unitCost` as a bare net figure with no VAT term at all (`Dr Inventory (full unitCost) / Cr AP (unitCost − withheld) / Cr WHT (withheld)`).
- **Worth knowing: the codebase's two existing "auto RR" paths don't actually agree with each other today.** The PO-linked flow (`ReceiveAgainstPoModal.tsx`) hardcodes `vatTreatment: 'inclusive'` and shows a read-only VAT/withholding breakdown. The PO-less flow (`ReceiveStockModal.tsx`) sends no `vatTreatment` at all, silently falling back to the DTO's `exclusive` default, and shows no VAT anywhere in its UI. Manual RR is modeled on the PO-linked flow's behavior here (inclusive-by-default, VAT and withholding both visible), since that's the one that actually deducts and surfaces VAT the way the developer confirmed above — not the PO-less screen's silent-exclusive, VAT-invisible behavior.

### Frontend

- "New Manual RR" action added to `ReceivingReportsList.tsx` (`/accounting/receiving-reports`), opening a modal derived from the existing `CreateManualRrModal.tsx`.
- The **Source** field (labeled "Source," not "Supplier" — see Decisions) and the Item field both change from search-only comboboxes to **search-or-create** comboboxes — typing something with no match surfaces a "Create new…" option instead of a dead end. Location, Serial Number, Reason, and Notes are unchanged from today's form.
- **New financial block, none of which exists on today's `CreateManualRrModal.tsx`**: Unit Cost, a **VAT Treatment** dropdown (Inclusive / Exclusive, defaulting to Inclusive), a computed **Input VAT** line, a **Withholding** select, and a computed **Withheld Amount** — all shown together as one group, matching `ReceiveStockModal.tsx`'s header layout. See the calculation spelled out above.
- The owner-facing approve/reject views (`ManualRrList.tsx`, `ManualRrDetailView.tsx`) relocate alongside it under Accounting, so the second-approver requirement is unchanged.
- `ItemSearchCombobox` is currently imported from the Inventory purchase-requests folder — reused here (extended with the "create new" affordance) rather than rebuilt; an implementation detail, not a design blocker.

### RBAC

- Today: one permission, `inventory:manual-rr:create`, seeded to Business Owner only, gating submit/approve/reject/read alike.
- **Decided**: a new `accounting:manual-rr:create` permission in Accounting's own namespace — mirroring Scenario 36's deliberate choice to give Accounting its _own_ permission for RR visibility rather than borrowing `inventory:*` — seeded to Business Owner + Accountant.

## Parts to build — confirmed scope, `implement-scenario` run starting 2026-09-19

Retiring the orphaned Inventory shell is **not in scope this run** (developer chose "keep both live"). Each part below gets its own e2e coverage (backend and/or frontend, as applicable) and manual test steps, and stops for developer confirmation before the next begins.

1. **Backend find-or-create** — a shared helper used by `submit()` for both `supplierId` (labeled "Source") and `itemId`: resolve an existing row by id/name, or create a minimal one from the typed name. Creating a new Source requires `defaultInputVat`/`defaultWithholding` in the same call — no silent default.
2. **Fuzzy-duplicate detection** — before find-or-create actually creates a new Source or Item, check existing rows for a likely near-duplicate name and return that match so the frontend can warn ("Did you mean the existing '…'?") instead of silently creating a second, near-identical record.
3. **VAT/WHT parity fix in `approve()`** — the real, independent bug found while checking Directive 4: resolve Input VAT off `supplier.defaultInputVat` at the flat rate exactly like `receiveStock()`, split net cost vs. VAT per the VAT Treatment (Inclusive/Exclusive) chosen, post `Dr Input VAT`, add the typed `withheldAmount` override, and recompute `netApAmount` to include VAT. Testable standalone against today's Inventory-side Manual RR, before any UI relocation — good candidate to build/verify first.
4. **Frontend combobox upgrade** — the Source and Item fields on `CreateManualRrModal.tsx` gain the "Create new…" affordance, the new-Source VAT/withholding fields, and the Part 2 duplicate-warning step.
5. **Frontend financial block** — add the VAT Treatment dropdown, computed Input VAT, Withholding select, and computed Withheld Amount to the form, matching `ReceiveStockModal.tsx`'s layout.
6. **Frontend relocation** — create action added to `/accounting/receiving-reports`; approve/reject views moved alongside it.
7. **RBAC** — new `accounting:manual-rr:create` permission, seeded to Business Owner + Accountant.

## Risks

- **Catalog/supplier-list growth.** Every one-off manual RR against a new name permanently adds a row to `Supplier` or `Item`. Fine at occasional volume; worth revisiting if this becomes a frequent path (see Open Question 4).
- **Minimally-filled records surfacing elsewhere.** An auto-created Item with no category/price, or a Supplier with no payment terms, might render oddly on screens built assuming those are always set (Open Question 3).
- Moving creation into Accounting means an Accountant, not a Stock Controller, becomes the one originating physical serial numbers and, now, new catalog items — worth a sanity check with whoever owns warehouse operations before this ships, even though Business Owner already had this power today.

## Implementation Log — 2026-09-19

**The design changed twice more after "Parts to build" above was written, both mid-implementation, both developer-directed:**

1. Manual RR needed to support **items not in the catalog at all** ("Something else"), not just suppliers that aren't registered — the single biggest reason a manual RR exists in the first place. This meant find-or-create applies per _line item_, not just to the header-level Source.
2. Once that was in place, the developer flagged that a **single-line** document was the wrong shape entirely: "the RR in inventory is better except that it doesn't have an option to choose 'other'." The feature was rebuilt a second time into a genuine **multi-line** document mirroring the normal Create Receiving Report screen line-for-line (header fields, a lines table, VAT/withholding at the header applied across the whole document) — with catalog-optional escape hatches layered on top, not a parallel, simpler form.
3. In the same pass, the lifecycle was simplified: **no approval gate at all.** "After draft the accountant can post it immediately, no need [for] approval or anything" — the RR-05 self-approval-blocked/second-approver design (the entire premise of "Parts to build" items 1–7 above) is **fully superseded**. `ManualReceivingReportStatus` is now `draft | posted`, not `pending | approved | rejected`.

**What was actually built, reflecting the final design:**

- **Backend, full rebuild**: `ManualReceivingReport` is now a header model with a `ManualReceivingReportLine[]` child table (`manual_receiving_report_lines`) — hand-written migration `20260919103608_manual_rr_multiline_draft_post` (destructive drop/recreate, safe since the table was empty in both dev and test DBs, verified before applying). Header carries warehouse, `receivedAt` (optional "Date Received"), delivery receipt no., driver/helper names, reason, notes, source (`supplierId` or `newSourceName` + required VAT/withholding defaults for a new one), and document-level VAT treatment/withholding. Each line carries `itemId` or `newItemName`, quantity, unit cost, and per-line serial numbers. No PO/transfer linking anywhere in this flow, by design.
- **Find-or-create, deferred to `post()`, not `create()`/`update()`**: a line's item and the header's source resolve (or originate) only at post time — a draft stays freely re-editable without orphaning a catalog row on every edit. A new item's `isSerialTracked` is inferred from whether serials were typed for that line, not forced.
- **`post()`** — the only place stock actually moves: validates every line's serial count against its resolved item's serial-tracked-ness, checks for duplicate/already-registered serials across the whole document, aggregates VAT (inclusive backs it out of the line totals, exclusive adds it on top) and withholding across all lines into one JE, then in one transaction originates serials or upserts `StockBalance` per line, writes `StockLedger`/`StockCostLayer`, posts one aggregated journal entry, and flips the header to `posted`. A DRAFT AP Bill is then best-effort scaffolded against the resolved source, exactly like a normal receiving report's own post-time behavior — this is what makes "payment" fall out for free, per Directive 4's original point.
- **New `accounting:manual-rr:create` permission**, seeded to Business Owner + Accountant via their existing `accounting:*:*` wildcard — no role-permission seed change needed, only the permission catalog entry itself.
- **Frontend, full rebuild to match**: `ManualRrForm.tsx` is now a multi-line create page (`useFieldArray`) — each line independently toggles Catalog item / Something else, with a per-line serial capture UI once a line resolves to (or is marked as) serial-tracked. Header fields match the normal RR screen's own set minus PO linking, plus the VAT Treatment / Withholding selects (shown once any line carries a cost) and the Source toggle (Registered / Other, with the new-source VAT/withholding fields shown inline when "Other" is picked). `ManualRrDetail.tsx` replaced Approve/Reject entirely with a single **Post** action (plus **Delete Draft**, draft-only) — no self-approval-block UI logic remains, matching the no-approval-gate decision. `ManualRrPanel.tsx` now lists open **drafts** (`status: 'draft'`), not pending approvals.
- **Dead code removed, not just left behind**: the fully-orphaned Inventory-side modal components (`CreateManualRrModal.tsx`, `ManualRrDetailView.tsx`, `ManualRrList.tsx` — confirmed unreferenced anywhere, per `CountingHub.tsx`'s own comment that this folder "has no page.tsx") and their matching submit/approve/reject server actions were deleted outright rather than patched to a new API they no longer make sense under. The Inventory-side controller route prefix, the shared service, and the `inventory:manual-rr:create` permission itself were kept live (per the earlier "keep both live" decision) — the Accounting UI is simply the only reachable entry point into the same backend now.
- **Backend e2e**: `backend/test/manual-receiving-report.e2e-spec.ts` fully rewritten — 19 tests, all passing, covering draft CRUD, permission checks, find-or-create for both serial-tracked and non-serial-tracked new items, serial validation, same-actor draft→post with no approval, double-post prevention, VAT/withholding parity across inclusive/exclusive treatments, and AP bill drafting.
- **Frontend e2e**: `frontend/e2e/manual-receiving-report.spec.ts` fully rewritten for the multi-line/draft-post flow (one catalog line + one "Something else" line, save draft, post, confirm status flips) — demonstrated passing end-to-end multiple times in isolation.

**Two real bugs found and fixed along the way, not part of the original plan:**

- **Zero-VAT bug (the thing "Parts to build" item 3 above was written to fix)** — confirmed still real in the old single-item code, and carried the same fix forward into the multi-line rebuild: Manual RR previously posted the full typed cost with no VAT component at all. Now resolves Input VAT the same way `receiveStock()` does, aggregated across every costed line.
- **Frontend `'' vs undefined` bug**: an unset `SearchableSelect`/combobox value is `''`, not `undefined`. Sent as-is for `supplierId` (header) or `itemId` (a "Something else" line), this reads to the backend as a non-null but non-existent foreign key and throws a raw DB constraint violation instead of being treated as "not set." Fixed in `ManualRrForm.tsx`'s submit payload for both fields.

**Worth flagging:**

- **Fuzzy-duplicate detection ("Parts to build" item 2) was not built.** It made sense against the original single-supplier/single-item design; once find-or-create moved to per-line items plus the header source, and the whole feature was rebuilt twice more, this was dropped rather than carried forward unexamined. Worth a fresh, explicit decision with the developer if this is still wanted — likely scoped as its own follow-up rather than reopening this scenario.
- **No frontend edit-draft page.** The backend's `PATCH /:id` (full-replace update) exists and is exercised by the e2e suite, but there is no UI to reuse `ManualRrForm.tsx` against an existing draft — today a draft can only be viewed, posted, or deleted, not edited, from the UI. Flagged as a deliberate scope cut under time pressure, not an oversight; revisit if drafts start needing correction before posting in practice.
- **An unrelated, pre-existing environment issue surfaced while verifying the frontend e2e spec**: the isolated e2e stack's `next dev` process occasionally reloads mid-test and the browser lands back on the previously-rendered route, for reasons unrelated to this feature's own code (ruled out: video-recording-triggered file-watch churn — disabling video did not change the failure rate). The full flow has been demonstrated passing cleanly multiple times in isolation; the occasional failure is this dev-server-level flakiness, not an application bug. Worth a dedicated investigation outside this scenario's scope, since it would affect any frontend e2e spec, not just this one.
- **`stock-receiving-gl-ap-posting.e2e-spec.ts`'s own "Part 6" section remains blocked by a separate, pre-existing, unrelated bug**: its `beforeAll` does `prisma.supplier.findFirstOrThrow()` against a freshly-seeded test DB that has zero suppliers (the real seed script deliberately strips fictional demo suppliers) — not caused by this scenario's changes, flagged to the developer, not fixed here (out of scope).

## Implementation Log — 2026-09-19 (2nd pass, same day)

**Two more developer-directed changes landed after the first Implementation Log above, both same day:**

1. **Driver/Helper swapped for Supplier Invoice No. / PO Number.** These are the same kind of paper-trail reference field as `deliveryReceiptNumber` already was — never a real link (a manual RR has no PO context by design), just somewhere to note one down if the physical paperwork has it. 2. **VAT/withholding rebuilt a second time — now driven solely by one per-document toggle, never by the resolved source.** The developer walked through the existing "normal RR" precedent first (there are two: the PO-linked screen hardcodes VAT-inclusive and reads withholding purely off the supplier's own profile with no UI at all; the PO-less "Receive Stock" screen exposes separate VAT/withholding dropdowns but never displays what it computes) and then set the actual rule for Manual RR, which matches neither exactly:
   - **One dropdown, "VAT Treatment": Inclusive / Exclusive, defaulting to Inclusive.** No separate Withholding dropdown, no typed override fields — "no other fields, just that."
   - **Inclusive** backs 12% VAT out of every costed line's typed amount **and** applies 1% withholding on the resulting net — both together, off the one toggle.
   - **Exclusive** computes neither. The typed amount is final, as entered — no VAT, no withholding.
   - Deliberately **not** derived from the resolved source's own `defaultInputVat`/`defaultWithholding` — a new "Other" source still collects those (so its Supplier record behaves correctly wherever else it's reused later), but they no longer drive _this_ document's own math. Confirmed by dedicated backend e2e coverage using a source with `defaultInputVat: 'none'` and still getting VAT computed under Inclusive.
   - Backend: `ManualReceivingReport.withholding`/`vatAmountOverride`/`withheldAmountOverride` columns dropped entirely (migration `20260919125009_manual_rr_vat_toggle_line_discounts`); `post()`'s tax block rewritten around a single `applyTax = (vatTreatment ?? 'inclusive') === 'inclusive'` check.
3. **Line-item costing rebuilt to match the Purchase Order line grid** (the developer's reference screenshot): each line now carries `srp`/`discounts`/`isFreebie`, the same cascading discount-chain math and JSON shape as `PurchaseOrderLine` (`POLineDiscountType`, reused rather than duplicated). Unit Price auto-computes from SRP + the discount chain when an SRP is set, exactly like the existing RR/PO screens' own `costFromPricing`/`unitFromChain` pattern — a hand-typed cost (the common case for a "Something else" line with no catalog SRP) is never overwritten.
