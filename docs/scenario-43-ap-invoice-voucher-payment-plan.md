# Scenario 43 — AP Invoice Tables, Payment Field Carry-Over & System-Generated Voucher — Gap Analysis & Closing Plan

Source: developer's original 4-item comment (undated in this doc's own history, restated 2026-09-01), illustrated with two reference screenshots from the client's legacy accounting tool: a standalone **Payments** list (Date/Reference/Paid from/Description/Payee/Accounts/Amount/Voucher #) and a printed **Payment** voucher (letterhead, Date/Reference/Voucher #, an Account→Total table, Prepared By/Certified By/Approved By signature blocks, and an "Acknowledged receipt of payment" signature line). Planning only per explicit instruction — nothing in this doc has been implemented yet.

## The scenario we're building toward

Today, AP Bills (Scenario 41, same session) already produce a branded "Purchase Invoice" document and have a working two-step voucher approval flow. This doc closes the gap between that and the client's own legacy paper trail — a **Payment** voucher, not just a Purchase Invoice, with its own account breakdown, its own system-assigned number, and a real approval/audit chain, plus a way to actually browse payments the way the reference screenshot's list does (which doesn't exist anywhere in the app today, discovered during this doc's research pass).

## What's already done ✅ (verified this session, file/line cited)

1. **Item 2, "Remove the AP number" — already done**, in this same session's Scenario 41 Part 4: `APBill.billNumber` is no longer auto-generated (was `` `AP-${Date.now()}` ``) — it's now required to be the supplier's own invoice number, with `@@unique([supplierId, billNumber])`. See [scenario-41](./scenario-41-purchase-invoice-naming-plan.md). Nothing left to do for this item.
2. **Payment-record field carry-over is already real, not just captured** — `APBill.sourceOfPayment`/`referenceNumber`/`serialNumber` (`schema.prisma:1144-1155`) are captured once on the bill; `recordPayment()` (`ap-bills.service.ts:1011-1023`) copies them onto the new `APPayment.method`/`.reference`/`.chequeNumber` on every payment, not re-asked at Record Payment time. `RecordAPPaymentDto` has no method/reference/cheque fields of its own — it only takes `amount`/`paymentDate`/`notes`/`bankAccountId`.
3. **A real two-step voucher approval system already exists**: raise → `pending_online_approval` → `pending_onsite_approval` → `approved` (or `rejected` from either stage), enforced status transitions (`requireVoucherStatus`), a reject-reason capture, and file attachments via the generic `FileAttachments` subsystem — all in `VoucherPanel.tsx` + `ap-bills.service.ts`'s four voucher endpoints.
4. **Voucher actions are already fully audit-logged** — `createVoucher`/`approveVoucherOnline`/`approveVoucherOnsite`/`rejectVoucher` all call `logBillAudit()` with before/after snapshots (`ap-bills.controller.ts:195-265`). Minor incompleteness: the snapshot (`snapshotBill()`) doesn't capture `voucherRejectedReason`, or the approver id/timestamp fields — worth closing alongside whatever else this doc builds, not a reason to rebuild the audit trail from scratch.
5. **AP Bill's printed "Purchase Invoice" already has a real items table and a real signature-free totals block** (Scenario 41 Part 1, `buildAPBillHtml()`) — this doc doesn't touch that template; it adds a second, distinct document (the Payment voucher) and a second, distinct table (Account breakdown) the Purchase Invoice doesn't currently have.

## What's not done / gaps ❌⚠️

1. **No GL-account breakdown table anywhere** — the printed Purchase Invoice's items table is sourced only from matched Goods Receipt lines (Item/Qty/Unit price/Total); a bill with no PO/receipt (a general/manually-entered bill) renders that table **completely empty**, with no fallback account/amount row at all. The on-screen bill detail page's Subtotal/Tax/Withholding/Total block is a CSS label/value grid, not an HTML `<table>`, unlike the client's reference. `APBill.expenseAccountId` (`schema.prisma:1143`) is a single, unvalidated `String?` scalar with no Prisma relation and no per-line granularity — one override account for the whole bill, nothing like the reference's clean "Account | Total" rows.
2. **No standalone Payments list anywhere in the app** — confirmed via full route/service grep of both repos: no `GET /ap-bills/payments`-style endpoint, no `aPPayment.findMany()` call anywhere in the backend outside one bill's own `findOne()`, and no frontend route lists `APPayment` rows across bills. `APBillDetail.tsx`'s per-bill "Payment history" section is the only place a payment is ever visible today — nothing matches the reference screenshot's cross-bill list (Date/Reference/Paid from/Description/Payee/Accounts/Amount/Voucher #).
3. **Voucher numbers are manually typed, not system-generated** — `CreateVoucherDto.voucherNumber` is a caller-supplied required string (`dto/ap-bills.dto.ts:246-251`); no generation logic exists anywhere. A duplicate typed-in number surfaces as a raw Prisma unique-constraint error today (`createVoucher()` only pre-checks "this bill already has a voucher," not global uniqueness).
4. **A voucher cannot be edited after it's raised** — once `voucherNumber` is set, `createVoucher()` itself refuses to run again, `UpdateAPBillDto` has no voucher fields at all, and `VoucherPanel.tsx` only exposes the four status-transition actions (approve-online/approve-onsite/reject) — nothing lets a value on the voucher itself change post-creation.
5. **No distinct "head approval" tier exists** — a single permission, `accounting:ap-bills:approve`, gates _both_ approval stages (online and onsite) and rejection. There's no separate role/permission for a "head"-level approver distinct from whoever holds that one permission today (currently Business Owner + Accountant, per `seed.ts:3830-3905` — Branch Manager can raise a voucher via `ap-bills:voucher` but was deliberately excluded from `:approve`, a segregation-of-duties boundary that was later lifted for Accountant "by explicit developer decision, not an oversight," per that commit's own comment).

## Decisions (developer, 2026-09-01)

1. **Account table**: real Account breakdown, scoped narrowly — fixes the actual bug (a general/non-PO bill's item table renders completely blank today) rather than a cosmetic reformat. For a bill with no PO/goods-receipt lines, show one row: the resolved expense account (`expenseAccountId`, falling back to `supplier.defaultExpenseAccount` — the same fallback the backend already posts with, so the printed figure matches what actually hit the GL) against `totalAmount`. A PO-linked bill keeps its existing item-level table as-is — already more informative than a single account row. **No new per-line account granularity on `APBill`** (i.e. not the `BusinessExpense` multi-line treatment) — out of scope here.
2. **Payment voucher is a real third document, replacing "Cheque Payment."** The existing `renderApChequeBody()` print (thin label/value list, no letterhead, no Account table, no signatures) is retired in favor of a new bespoke `buildAPPaymentVoucherHtml()` — a proper superset (still shows method/reference/cheque #, adds the Gap-1 Account table, Prepared By/Certified By/Approved By, and an acknowledgment-of-receipt line), in the same branded family as Purchase Order/AR Invoice/Purchase Invoice.
3. **Standalone Payments list: build it, minimally.** Real, standing gap — an Accountant has no way today to browse payments except one bill at a time. Read-only: same columns as the reference (Date/Reference/Paid from/Description/Payee/Accounts/Amount/Voucher #), each row linking to its parent bill. No separate create/edit flow — Record Payment on a bill remains the only way a payment is created.
4. **Voucher number**: system-generated, simple tenant-wide sequential — matching this codebase's own `generateCode()`-style convention (e.g. Purchase Orders' `PO-#####`), not the reference's prefix-coded scheme.
5. **Editable after creation**: locked once `approved`; before that (`pending_online_approval`/`pending_onsite_approval`), "editable" means **void the voucher, then raise it fresh** — not in-place field edits. (There's no longer a manually-typed number to correct once it's system-generated, so a clean void-and-reraise is the more honest mechanism than pretending there's a field to edit.)
   5a. **Found during implementation, decided 2026-09-01**: a naive void (nulling `voucherNumber`) would let a fresh raise regenerate the _identical_ number string, since `generateVoucherNumber()` derives "next" from the current max — reused numbers are exactly the kind of thing that undermines "keeps an audit trail." Decided: **voided numbers are retired permanently, like a voided check, never reissued** — `voidVoucher()` does NOT clear `voucherNumber` (it stays on the row as a historical record); a new `voided` status was added to `VoucherApprovalStatus` instead. `createVoucher()`'s "already has a voucher" guard now checks `voucherApprovalStatus` (blocks on anything except null/`voided`) rather than `voucherNumber` presence.
6. **Head approval**: no new tier. The existing single `accounting:ap-bills:approve` permission (currently Business Owner + Accountant, not Branch Manager) already satisfies this — no schema/permission change needed for this specific item.

## Closing the gaps

### A. System-generated voucher numbering + void-and-reraise

`createVoucher()` drops `CreateVoucherDto.voucherNumber` as caller input — generates a sequential number server-side instead (max-based, matching the pattern already fixed elsewhere in this codebase for the same class of bug — see Scenario 27's `generateCode()` `.count()` → max-based fix in `purchase-order.service.ts`/`stock.service.ts`/etc., not the fragile `.count()`-based approach). New `voidVoucher()` action, callable only while `voucherApprovalStatus` is `pending_online_approval` or `pending_onsite_approval` — clears `voucherNumber`/`voucherApprovalStatus` back to null so `createVoucher()` can run again cleanly. New audit action (`VOID_VOUCHER`) alongside the existing `RAISE_VOUCHER`/`APPROVE_*`/`REJECT_VOUCHER`.

### B. Account breakdown table

Backend: resolve the effective account (`expenseAccountId` → `supplier.defaultExpenseAccount` fallback) into `getDocument()`'s response so the frontend doesn't have to guess the fallback independently. Frontend: real `<table>` (Account | Total) on both `APBillDetail.tsx` (replacing the relevant slice of the current CSS-grid figures where it applies) and in `buildAPBillHtml()`'s printed Purchase Invoice, shown only when there are no goods-receipt item lines to show instead.

### C. Payment voucher document

New `buildAPPaymentVoucherHtml()` in `printInventoryDocument.ts`, same family style as the other bespoke prints, replacing `renderApChequeBody()`/its call site in `APBillsList.tsx`. Includes: letterhead, Date/Reference/Voucher #, description, the Gap-B Account table, Prepared By/Certified By/Approved By signature blocks, and an "Acknowledged receipt of payment from {enterprise}" signature/date line, matching the reference exactly.

### D. Standalone Payments list

Backend: new `GET /ap-bills/payments`-style endpoint — a real `aPPayment.findMany()` across bills (doesn't exist anywhere today), joined out to the parent bill's supplier (Payee), resolved account (Accounts, reusing Gap B's resolution), and `bankAccountId → BusinessBankAccount.name` (Paid from). Frontend: new list route/page under `accounting/ap-bills/payments`, same columns as the reference screenshot, each row linking to `/accounting/ap-bills/{billId}`.

## Not in scope for this doc

- Scenario 41's own 4 parts (Purchase Invoice naming/PDF, PO→Invoice visibility) — already done, separate doc.
- A new "head approval" permission tier — explicitly decided against (Decision 6).
- Per-line/multi-account breakdown on `APBill` (the `BusinessExpense`-style redesign) — explicitly decided against (Decision 1).

## Implementation Log — 2026-09-01

**For this scenario, I have done:**

- **Part A** (Closing the gaps A) — `voucherNumber` is now system-generated (`V-<yyyymmdd>-<seq>`, max-based, mirroring the PO/PR code-generation pattern), never typed in; `CreateVoucherDto` deleted. New `voidVoucher()` — callable only while a voucher is still pending (either approval stage) — lets a bill be raised fresh. **Decision 5a** (found during implementation, developer-confirmed): voided numbers are retired permanently, not reused — a new `voided` status on `VoucherApprovalStatus` (migration `20260901095852_voucher_voided_status`) replaces the original "clear voucherNumber back to null" design, so a voided number stays on the row as a historical record and `generateVoucherNumber()` never reissues it. `createVoucher()`'s guard now checks `voucherApprovalStatus` (blocks on anything except null/`voided`) instead of `voucherNumber` presence. `VoucherPanel.tsx` updated to match (no more manual-number input; a "Void" action during either pending stage; a "previous voucher was voided" note). 19+ existing e2e call sites across `purchasing-ap.e2e-spec.ts`/`accounting-audit-log-ap-bills.e2e-spec.ts` fixed for the removed manual-number behavior; new coverage added for void (both files) including the retire-not-reuse guarantee.
- **Part B** (Closing the gaps B) — `APBill.expenseAccountId` promoted from a bare unvalidated string to a real Prisma relation (migration `20260901112519_ap_bill_expense_account_relation`; confirmed safe first — 0 existing bills had it set). `getDocument()` now resolves the same 3-tier fallback `receive()` already posts with (bill override → supplier default → tenant `DEFAULT_EXPENSE` mapping, the third tier not in the original plan text — found while reading `receive()`'s actual posting logic, added for correctness so the printed figure always matches what actually hits the GL) into a new `effectiveExpenseAccount` field, safely degrading to `null` if the tenant mapping isn't configured rather than failing the whole document. Deliberately NOT added to `findOne()` itself (reused internally by ~10 other bill actions that don't need it, and the tenant-mapping tier can throw). Both `buildAPBillHtml()` (print) and `APBillDetail.tsx` (on-screen — resolves tiers 1-2 only, client-side, from data `findOne()` already includes; the rare tier-3-only case shows correctly in print but not on-screen, an accepted minor asymmetry) now show a real `<table>` Account/Total row in place of the goods-receipt item table specifically when a bill has no matched receipts.

- **Part C** (Closing the gaps C) — new `buildAPPaymentVoucherHtml()`/`printAPPaymentVoucherDocument()` in `printInventoryDocument.ts`, replacing the old cheque-only `renderApChequeBody()`/`printCheque()` in `APBillsList.tsx` (now `latestPayment()`/`printPaymentVoucher()`, triggered for any payment, not just cheque ones). `getPaymentDocument()` extended to carry `voucherNumber` (the bill's, not per-payment — this system raises one voucher per bill as pre-payment authorization, unlike the client's reference where each payment row had its own; using the bill's voucher is the correct fit for how this system's approval flow actually works), `description`, and `effectiveExpenseAccount` (reusing Part B's resolver) alongside what it already had. `documentType` renamed `ap_payment_cheque` → `ap_payment_voucher`. The new template matches the reference exactly: letterhead, Date/Reference/Voucher #, description, Account table (against the payment's own amount, not the whole bill's — a bill can be paid across several payments), Prepared/Certified/Approved-By signature blocks (left blank for physical sign-off, matching the reference's own paper-form convention — not auto-filled from the voucher's approval timestamps, which would need a separate user-name lookup out of scope here), and the "Acknowledged receipt of payment from {enterprise}" line. Found and fixed in passing: `getDocument()`'s and the new `getPaymentDocument()`'s enterprise lookups never selected `address`, so the Part 1 Purchase Invoice's own enterprise block had silently always shown "—" — both fixed. One existing e2e assertion (`purchasing-ap.e2e-spec.ts`) updated for the renamed `documentType`.

**Found and fixed live during manual testing (2026-09-01)** — not part of the original 4 items, but blocking verification of Part A/B: `APBillsList.tsx`'s list ordering was `orderBy: { billDate: 'desc' }` alone. Every bill entered "today" shares the same `billDate`, so ties had no defined secondary order — creating or editing a bill (e.g. filling in a Pending-SI draft's invoice number) could leave it anywhere in the list with no visible connection to the action just taken, reading as "nothing saved" even though it had. Fixed: `orderBy: [{ billDate: 'desc' }, { updatedAt: 'desc' }]` — the bill you just touched is now always near the top. Verified via a direct API call and a full Playwright-driven browser session (login → edit → save → confirm persisted) before finding this — the save itself was never broken, only its visibility in the list.

- **Part D** (Closing the gaps D) — new `GET /ap-bills/payments` (`APBillsService.listPayments()`), a real cross-bill `aPPayment.findMany()` — confirmed nothing like it existed anywhere before this. Registered before `GET /ap-bills/:id` in the controller (route-order matters in Nest — `:id` would otherwise greedily match `payments`). Joins out to the parent bill's supplier (Payee), reuses Part B's `resolveEffectiveExpenseAccount()` for the Accounts column, and batch-resolves `bankAccountId → BusinessBankAccount.name` for "Paid from" with one follow-up query rather than a schema relation — `APPayment.bankAccountId` has no Prisma relation today, and a concurrent Bank Reconciliation scenario (Scenario 42, a different session, found live in `schema.prisma` while working on this) is already actively using that same column, so a migration here was deliberately avoided to not risk colliding with that in-progress work. Same tie-break fix as the bills-list bug above, applied proactively: `orderBy: [{ paymentDate: 'desc' }, { createdAt: 'desc' }]`. Frontend: new `/accounting/ap-bills/payments` route (`APPaymentsList.tsx`), read-only, same columns as the reference (Date/Reference/Paid from/Description/Payee/Accounts/Amount/Voucher #), each row linking to its parent bill; a "Payments" button added to the AP Invoices list header for discoverability. Verified live via a Playwright-driven browser session (direct navigation and via the new nav button) — correct title, headers, and empty state, no console errors.

**Worth flagging:**

- Part D's page was only verified against the empty state live (no payments exist yet in the dev DB) — the field-mapping logic (Payee/Accounts/Paid-from resolution) is covered by careful code review and the same helpers Parts B/C already exercise, but hasn't been seen live with real populated rows yet. Worth a real look once an actual payment is recorded.
- Part B's on-screen/print asymmetry for the tenant-mapping-only fallback case (noted above) — acceptable today since it only differs when a bill has no own override AND its supplier has no default expense account, but worth knowing if it's ever confusing in practice.
