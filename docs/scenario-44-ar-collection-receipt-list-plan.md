# Scenario 44 — AR Collections Receipt List & Collection Receipt Document — Gap Analysis & Closing Plan

Source: developer-provided reference screenshots from the client's (NIG Marketing) own legacy accounting tool — a standalone **Receipts** list (Edit/View/Date/Reference/Received in/Description/Accounts/Amount) and a printed **Collection Receipt** (`CR#...`) document (NIG letterhead, customer address, Date/Reference, an Account→Total table, Total). Scoped live this session (2026-09-01) against the current AR Invoices page (customer-rollup view, confirmed _not_ the target shape) and current code. Direct companion to Scenario 43 (same session) — that doc closes this identical gap on the AP side (a Payments list + Payment voucher document); this one is the AR mirror. Planning only — nothing implemented yet.

## The scenario we're building toward

Today, `ARInvoice` already has a branded printed document (`buildARInvoiceHtml`) and a per-invoice "Payment history" section on its detail page. This doc closes the gap between that and the client's actual paper trail — a **Collection Receipt** per payment (not per invoice), plus a way to browse collections across customers the way the reference screenshot's Receipts list does, which doesn't exist anywhere in the app today.

## What's already done ✅ (verified this session, file/line cited)

1. **Single-invoice AR payment recording already works correctly as generic accounting.** `ArInvoicesService.recordPaymentCore` (`backend/src/accounting/ar-invoices/ar-invoices.service.ts:989`) posts Dr Cash / Cr AR via `JournalPostingService`, capturing `amount`, `paymentDate`, `method`, `reference`, `bankAccountId`, `branchId`, `collectorId`, `notes` on `ARPayment` (`schema.prisma:788`). One payment always ties to exactly one invoice (`arInvoiceId` required, not a multi-invoice batch) — already matches the reference screenshot's one-row-per-receipt shape, nothing to change there.
2. **Collector and branch context are already captured, just not surfaced.** `Collector` (`schema.prisma:2750`, with `branchId`, `area`, `stubNumber`) and `ARPayment.branchId` are real, populated fields on every payment today — the reference's Victorias/collector context already exists in the data.
3. **The branded-document family already exists with a clear extension point.** `frontend/src/libs/print/printInventoryDocument.ts` already has `buildARInvoiceHtml` (:1141) and `buildAPBillHtml` (:1301) in the same letterhead style (logo, two-party header, Date/Reference, Account→Total table) the reference Collection Receipt uses. A new builder slots into this same family.

## What's not done / gaps ❌⚠️

1. **No standalone Receipts list anywhere in the app.** Confirmed via full grep of both repos: no `arPayment.findMany()` call anywhere outside `ARInvoice`'s own nested `findOne()` include, no `GET /ar-invoices/receipts`-style endpoint, no frontend route lists `ARPayment` rows across invoices/customers. `ARInvoiceDetail.tsx`'s per-invoice "Payment history" section (:231-241) is the only place a payment is ever visible today — same shape of gap Scenario 43 found on the AP side.
2. **No printed Collection Receipt document at all — not even a thin fallback.** Unlike AP (Scenario 43 found `renderApChequeBody()`, a bare label/value list to upgrade), AR payments have zero printable output today; `ARInvoiceDetail.tsx` only prints the invoice itself (`printARInvoiceDocument`, :39).
3. **AR collections post straight to Cash, not through an Undeposited Funds clearing account.** `recordPaymentCore` debits `MAPPING_KEYS.DEFAULT_CASH` (`ar-invoices.service.ts:888,1234`), unlike POS, which already routes cash through `POS_UNDEPOSITED_FUNDS` (`Undeposited Collections - Branch`, GL `1-01-015`, `coa-seed.service.ts:61-65`) pending bank deposit. The reference's "Received in: UNDEPOSITED FUNDS-VICTORIAS" implies AR collections should land in undeposited funds too — a real posting gap, not just a display one.
4. **`Undeposited Collections - Branch` is one single tenant-wide account today, not one per branch**, despite its name — `POS_UNDEPOSITED_FUNDS` resolves to one global GL account; branch is only tracked via the journal entry's own `branchId`. The reference shows a distinct "UNDEPOSITED FUNDS-VICTORIAS" label — open whether that needs to be a real separate GL sub-account per branch, or the same shared account with the branch name resolved for display from `branchId`.
5. **The reference's account-number suffix scheme (e.g. `45735CHVBN`) isn't fully reproducible from data we have.** Partially decoded — `VBN`-style suffixes plausibly trace to `prisma/data/List_Collector - Sheet1.csv`'s route codes (`VB N` = Victorias_North), and the same 5-digit+suffix format is confirmed already present in `prisma/data/Aging_Accounts Receivable - Final_Aging.csv` (e.g. `00181CHBN`, `01203JJNP`) — but the recurring `CH` prefix seen across most rows isn't explained by anything in our data. Needs the client's own definition before this can be generated rather than just stored as an opaque imported string.
6. **Reference/CR numbering is free-typed, not system-generated.** `ARPayment.reference` (`schema.prisma:831`) is a plain optional string — no sequence/generator exists, unlike Scenario 43's planned system-generated voucher number for AP.

## Decisions (developer, 2026-09-01)

1. **Location: this IS the AR Invoices page**, not a new sibling route — confirmed, refined after Phase 1 re-verification found `ARInvoicesList.tsx` (2,234 lines) is not just the customer-rollup table — it also owns all of AR Invoices' CRUD (New Invoice, Send, Record Payment via `PaymentDialog`, Credit Memo, Debit Memo, Void, Delete, Payment History). **Narrowed scope, confirmed**: only the top-level, unfiltered `/accounting/ar-invoices` landing view swaps from the customer-rollup table to the Receipts register (Date/Reference/Received in/Description/Accounts/Amount). The dedicated customer route (`/accounting/ar-invoices/customer/[id]`) — full invoice list + all existing actions (New Invoice, Send, Record Payment, Credit/Debit Memo, Void, Delete) — stays exactly as-is; nothing here removes or relocates that functionality, just one click deeper (pick a customer first) instead of from the landing page. The reference screenshot's "New Receipt" button is an alias for the existing "Record Payment" flow (`PaymentDialog`), not a new creation flow — reached by picking a customer/invoice first, same as today. Non-destructive: the existing separate **AR Aging** report already covers the outstanding-balance-by-customer view, matching how the client's own legacy system keeps aging as its own separate report too (`Aging_Accounts Receivable - Final_Aging.csv`).
2. **Editability**: editable, in the limited sense matching Scenario 43's AP voucher pattern — reference/notes fields only in place; anything touching the posted amount/account requires a void-and-reraise, not a silent in-place edit, since these carry a `journalEntryId`.
3. **Scope: AR-wide.** Every `ARPayment`, any invoice type — not scoped to just the installment/"MI" portfolio.
4. **Undeposited Funds posting: deferred, explicitly out of scope for this doc.** Real gap (see below), but not something Scenario 44 fixes — needs its own scenario.
5. **Per-branch Undeposited Funds account: deferred alongside #4.** Evidence from the reference screenshot (`UNDEPOSITED FUNDS-VICTORIAS` as one combined account-name string, not a separate account + branch column) suggests the client's real chart of accounts has a genuinely distinct, separately-named account per branch — worth carrying forward into whichever future scenario picks up #4.
6. **CR reference number: no new generator.** Stays exactly as it works today — a free-text field the cashier manually types in at the point of collection, matching the existing POS-required CR field (`referenceNumber`, required at checkout since the "Require a CR (collection receipt) number for every payment" change). This scenario only needs to capture/display what's already typed in.

## Closing the gaps

- **A. Rebuild the AR Invoices page as the Receipts register.** Backend: new endpoint backing this page — `arPayment.findMany` across invoices, joined to customer, resolved AR account, branch, bank/undeposited account — replacing whatever query currently backs the customer-rollup view. Frontend: `ARInvoicesList.tsx` reworked to the reference's columns (Date/Reference/Received in/Description/Accounts/Amount), each row linking to its parent invoice; existing Edit/View actions per row. The customer-rollup columns (Total/Paid/Outstanding/Due/Status/Statement) are retired from this page — already covered by AR Aging.
- **B. Collection Receipt document.** New builder in `printInventoryDocument.ts`, same branded family as `buildARInvoiceHtml`/`buildAPBillHtml` — letterhead, customer address block, Date/Reference (the cashier-entered CR number, per Decision 6), single Account→Total row, Total.
- **C. Editability** (per Decision 2). Reference/notes editable in place on `ARPayment`; a new void-and-reraise action for anything that would otherwise change the posted amount/account, mirroring Scenario 43's `voidVoucher()` pattern — new audit action alongside whatever `AccountingAuditLog` coverage already exists for `ARPayment`.

## Not in scope for this doc

- Scenario 11's two-step collector-issues-stub → cashier-remits-and-confirms workflow (its own Closing Gap 4, tickets `86d3fwwnb`/`86d3fwwne`) — this doc only covers documenting/browsing a payment that's already been recorded, not changing how or when it gets recorded.
- **Undeposited Funds posting (Gap 3 above) and a real per-branch Undeposited Funds account (Gap 4 above)** — both confirmed real gaps, explicitly deferred per Decisions 4-5. `recordPaymentCore` keeps posting Dr `DEFAULT_CASH` / Cr AR unchanged; this doc's "Received in" column just displays whatever `bankAccountId`/branch context is already on the payment, without fixing the underlying posting.
- A new CR reference-number generator — explicitly decided against (Decision 6); stays free-text/cashier-entered.
