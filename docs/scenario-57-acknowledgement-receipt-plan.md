# Scenario 57 — Acknowledgement Receipt for Non-Customer Collections — Gap Analysis & Closing Plan

Source: developer-scoped, live in chat 2026-09-21, no client ticket yet. Original ask: "Collections: Acknowledgement Receipts for non customer payments / payments... Receive the money then they will issue an acknowledgement receipt or collection receipt." The original ask also paired this with "Payment of retention" — the developer explicitly dropped retention from this scenario's scope the same session (see Decisions). Planning only — nothing implemented yet.

## Related ClickUp Tickets

None identified or linked yet. Per house rule, no ticket gets created, moved, or touched without an explicit go-ahead.

## The scenario we're building toward

Money that comes into Collections isn't always tied to a Customer or an open `ARInvoice` — e.g. a walk-in miscellaneous payment, a refund, or any other inbound payment the client wants formally receipted, but that today's Collection Receipt has no path to record. The client's description implies a fork at the moment money is received: staff decide whether to issue a **Collection Receipt** (a customer and invoice already exist) or an **Acknowledgement Receipt** (they don't). This scenario builds the second path only — the first (Collection Receipt) already exists and stays untouched.

## What's already done ✅ (verified this session, file/line cited)

1. **Collection Receipt's infrastructure is a directly reusable template.** The branded print-document family (`frontend/src/libs/print/printInventoryDocument.ts`, e.g. `buildARInvoiceHtml`/`buildAPBillHtml`), a real full-page create pattern (`receipts/new/page.tsx` + `NewReceiptForm.tsx` — explicitly built as "a real, dedicated 'New Receipt' page (not a modal)" per Scenario 44), and `JournalPostingService`/`MAPPING_KEYS` as the generic GL posting mechanism all already exist and need only be pointed at a new document type, not rebuilt.
2. **A working precedent for "money received now, not tied to a specific invoice yet" already exists.** `UnappliedCustomerCollection` (`schema.prisma:1319-1353`, `backend/src/accounting/unapplied-collections/unapplied-collections.service.ts`) posts Dr Cash / Cr a holding GL account from just `amount`, `paymentMethod`, `reference`, `notes` — no invoice required at the point of recording. It's still customer-bound today, but its posting shape (credit a suspense/holding account instead of AR) is exactly the shape this scenario needs.
3. **The app already tolerates "no linked party record, just a name" — on the money-out side.** `BusinessExpense` (`schema.prisma:1874-1963`) has a `payeeType` plus a free-text `payee` fallback (line ~1922-1923) for when there's no linked Customer/Supplier/Employee row. Proof the pattern this scenario needs (a party captured as text, not a foreign key) is already established elsewhere in the app, just not yet on the money-in side.

## What's not done / gaps ❌

1. **No non-customer collection path exists anywhere.** `CollectionReceipt.customerId` is a required, non-nullable FK (`schema.prisma:960-1020`); every payment-recording route (`POST /ar-invoices/:id/payments`, `POST /ar-invoices/bulk-payments`) requires an existing `ARInvoice`, and `recordPaymentCore()` derives the customer from that invoice (`backend/src/accounting/ar-invoices/ar-invoices.service.ts`, ~1766-1870). There is no endpoint or screen that accepts money without a known customer and invoice.
2. **No document type or model for "Acknowledgement Receipt" exists.** Confirmed no model, enum, or UI screen anywhere by this name. The only existing use of "acknowledg(e)ment" in the app is unrelated: a signature line printed on AP/Expense payment _vouchers_ — "Acknowledged receipt of payment from {enterprise}" (`printInventoryDocument.ts`, `buildAPPaymentVoucherHtml`/`buildExpenseVoucherHtml`) — the _supplier_ acknowledging _NIG's outbound_ payment, the opposite direction and a different document from what we're building here. Worth a visually distinct label so staff don't conflate the two.
3. **No generic "who paid us, unlinked to any record" field exists on the money-in side.** The one model that looks like it might fit — `Payment` (`schema.prisma:791-804`, has a bare `payer` string) — is confirmed dead code, zero references anywhere in `src/`. Don't build on it; its name would also collide if reused.
4. **No GL mapping key exists for a generic non-customer collection.** `UnappliedCustomerCollection`'s `UNAPPLIED_CUSTOMER_COLLECTIONS` key is the closest pattern but is wired specifically to `Customer`.

## Decisions (developer, 2026-09-21)

1. **Acknowledgement Receipt is a separate flow, not a variant of the existing "New Receipt" form.** Mirrors Scenario 46's own AP-vs-Expenses split (Decision 6: two separate doors for two separate transaction shapes) rather than adding an optional "no customer" toggle onto Collection Receipt's existing form.
2. **Full page, not a modal**, for the create screen — matching the precedent Collection Receipt itself just set (Scenario 44).
3. **"Who paid" is free text only.** No search or link to an existing Customer/Supplier/Employee record — closer to a digitized paper receipt book than a linked transaction. No party record is created or matched behind the scenes.
4. **Retention explicitly dropped from this scenario's scope.** The original ask paired "Acknowledgement Receipts for non-customer payments" with "Payment of retention" — the developer removed the retention half this session. (Unrelated aside for context only: there is a separate, already-shelved "Customer Retention" concept from Scenario 38 Gap 9 — invoice-side withholding released later, not a cash receipt — that has no bearing on this decision and was not what was being asked about here.)

## Open questions (not yet answered)

1. **Reason field** — free text, or a light dropdown (e.g. Refund Received / Reimbursement / Miscellaneous / Other)? Affects how reportable these receipts are later.
2. **Findability after creation** — is print-and-file sufficient, or does the list need to be searchable/filterable (e.g. by payer name, date, amount)? A list + detail page is planned either way (mirroring Collection Receipt's own), but search/filter scope isn't confirmed.
3. **Document number prefix** — proposed `ACK-YYYYMMDD-NNNN` (distinct from Collection Receipt's `CR-...`, and deliberately avoiding an `AR-` prefix since that already means Accounts Receivable everywhere else in this app) — needs confirmation, ideally against the client's own paper form if one exists.
4. ~~**GL treatment**~~ — **Resolved, 2026-09-21 (reversed same day — see Live-testing corrections #5).** Final answer: a real Chart of Accounts dropdown (`accountId`), not free text and not a fixed placeholder. Picking an account actually changes which account the receipt's credit line posts to, falling back to `MISC_COLLECTIONS` (`2-02-050`) when none is picked.
5. **Entry-point placement** — does Acknowledgement Receipt get its own sidebar/nav item under Collections, or a second button next to Collection Receipt's existing "New Receipt"? Affects discoverability, not the underlying logic.

## Closing the gaps (proposed, pending answers above)

- **A. New model + endpoint.** A new table (e.g. `AcknowledgementReceipt`) carrying `payerName` (free text), `reason`, `amount`, `paymentDate`, `method`, `bankAccountId`/`reference`, `notes`, `branchId`, `collectorId`, a system-generated `number`, `journalEntryId`, `cancelledAt`/`cancelReason` — mirroring `CollectionReceipt`'s own shape minus every customer/invoice field. One new endpoint to create it, posting Dr Cash-or-Bank / Cr the new holding account via `JournalPostingService`.
- **B. New full page + list/detail.** A "New Acknowledgement Receipt" page (free-text payer, reason, amount, date, method, notes) plus a list and a detail/print view — same shape as Collection Receipt's own `receipts/new` / `receipts/view`.
- **C. New print document.** A new builder in `printInventoryDocument.ts`'s branded family, visually distinct from the existing AP/Expense voucher's "Acknowledged receipt of payment" signature line.

## Not in scope for this doc

- **Retention** — neither the client's original "payment of retention" framing nor the pre-existing, unrelated, shelved Scenario 38 Gap 9 concept. Explicitly removed from this scenario by developer decision, 2026-09-21.
- Linking a payer to any existing Customer/Supplier/Employee record — decided against; free text only.
- Undeposited Funds routing / branch-specific holding accounts — an already-known, separately deferred gap (Scenario 44 Decisions 4-5). This doc's proposed holding account follows the same simple pattern without resolving that broader question.

## Live-testing corrections (developer, 2026-09-21)

Found and fixed during the developer's own click-through, after Part 1 was first reported done:

1. **"Source of Fund" relabeled to "Deposited To"** on the Acknowledgement Receipt form. Flagged by the developer ("why source of fund if we are the one receiving?") — the field names which bank account the money is deposited _into_, for Bank Reconciliation matching, not something funding an outgoing payment. The same fix was then extended to the two AR/money-in screens that had the identical, pre-existing mislabeling: Collection Receipt's own "New Receipt" page (`receipts/new/_components/NewReceiptForm.tsx`) and its legacy per-invoice quick-pay dialog (`ARInvoicesList.tsx`'s `PaymentDialog`). The AP-side occurrences (`ap-bills/payments/new/_components/RecordPaymentForm.tsx`, the AP voucher print) were left as-is — those really are outgoing payments, correctly labeled.
2. **Business Owner (no assigned branch) could not create a receipt at all.** The service's `create()` had copied `UnappliedCollectionsService.record()`'s hard `branchId`-required check verbatim, but the actual screen this scenario mirrors — Collection Receipt's `ArInvoicesService.recordPaymentCore()` — never requires `branchId`; it just stores whatever it's given, including `null`. Fixed to match: branch is now optional, saved as `null` for a non-branch-assigned caller. Re-verified against both the e2e suite and the live dev server as Business Owner.
3. **Entry point moved from Accounting to POS.** Per the developer's own notes, Acknowledgement Receipt belongs under **POS → Collections**, not Accounting's AR Invoices page — the whole `accounting/ar-invoices/receipts/acknowledgement/` route tree was deleted and rebuilt under `pos/collections/acknowledgement/`. The backend endpoint stays under `accounting/acknowledgement-receipts` unchanged (still a GL-posting concern, same as how POS Collections already calls into `ArInvoicesService` for Collection Receipt) — only the frontend route and page-level permission guard moved (`accounting:ar-invoices:read` → `pos:collections:manage`, matching the new host page; the underlying create/list API permissions were deliberately left unchanged at `accounting:ar-invoices:pay`/`:read`, since every role that needs this already holds both).
4. **A dedicated sidebar item, not buttons on the Collections page.** First tried as entry-point buttons on `CollectionsScreen.tsx`'s own header (superseded within the same session); developer asked for a real sidebar item instead. Added "Acknowledgement Receipts" to `SideBar.tsx`'s POS group, directly under "Collections", same `pos:collections:manage` permission — `CollectionsScreen.tsx` is back to its original, untouched state.
5. **Account became a real dropdown, reversing the same-day "just a text field" decision.** Compared against the client's reference tool screenshot again — developer clarified they wanted a genuine Account field added (not folded into `reason`), and then, after a first pass shipped it as free text, corrected once more to a real Chart-of-Accounts dropdown that actually drives the credit line's posted account (not cosmetic). Two migrations in sequence: `add_acknowledgement_receipt_account` (free-text `account` column, now superseded) → `acknowledgement_receipt_account_fk` (drops it, adds `accountId` FK to `Account`). Backend: `create()` now calls `JournalPostingService.resolveAccount(dto.accountId, MAPPING_KEYS.MISC_COLLECTIONS)` instead of always crediting the fixed mapping — same fallback-chain helper item revenue/COGS already use. Frontend: reuses the existing `CategorySelect` + `getAccounts()`/`accountsToCategoryOptions()` pattern from `ExpenseForm.tsx` rather than building a new picker.
6. **Form layout redone to match the client's reference tool, and "Deposited To" dropped entirely.** Developer shared the same reference screenshot a third time asking the create form to follow its structure (Date/Reference row, a "Paid by" section, an "Account" section, a "Description" field) rather than this app's usual two-column field grid — and confirmed the bank-account ("Deposited To") field isn't needed at all for this receipt type, since the Account picker already covers categorization and there's no Bank Reconciliation need here. Removed end-to-end, not just hidden: `bankAccountId` dropped from the Prisma model (migration `acknowledgement_receipt_drop_bank_account`), the DTO, the service, and the form — `method` (Cash/Card/etc.) stays as a simple field with no conditional requirement now that there's nothing to require alongside it. `reason` kept its column name in the schema but is labeled "Description" everywhere in the UI (form, list, detail, print) to match the reference tool's wording. One real test row the developer had created while manually testing (`payerName: "test payer"`, had a `bankAccountId` set) was cleared to unblock the migration.
7. **"Received in" section label restored — but wired to bank accounts, not the Chart of Accounts, correcting a mixup from #6.** The reference tool actually has two separate "Account"-labeled fields: "Received in → Account" (which of the tenant's own bank/cash accounts the money landed in) and a line-item "Account" (GL categorization). Item #6 conflated these into one field and, based on "deposited to is not needed," dropped the bank-account concept entirely — live-testing caught it ("shouldn't this be the bank accounts?", pointing at the Chart-of-Accounts dropdown sitting under a "Received in" label). Corrected: `bankAccountId` restored end-to-end (new migration `acknowledgement_receipt_restore_bank_account`, DTO, service — informational only, same posture as `CollectionReceipt`'s own `bankAccountId`, doesn't change which account is debited), and the form now has both fields distinctly: "Received in" (bank accounts, plain `<select>`) followed by a separate "Account" field (the `CategorySelect`/Chart-of-Accounts picker that actually drives the credit line, unchanged from #5) right before "Description".
8. **The printed/detail document itself rebuilt to match the client's real Acknowledgement Receipt exactly.** Developer shared an actual example of the client's document (payer name, Date/Reference, "NIG MARKETING CORPORATION" letterhead block, a bold "PAYMENT FOR CASH ADVANCE"-style description line, a single `#`/Account/Total table row, and two signature blocks — Prepared by / Certified by, no third "Approved by" block) — a real document, not the earlier generic mockup. The previous label/value-row layout (Received From, Payment Method, Reference No., Branch as separate rows) is gone; both `AcknowledgementReceiptDetail.tsx` and `buildAcknowledgementReceiptHtml` now mirror `CollectionReceiptSheet.tsx`'s original 3-column header + account-table shape (the one `buildCollectionReceiptHtml` deliberately moved _away_ from for Collection Receipt itself, since a partial payment showing an invoice's full account table was misleading — that problem doesn't apply here, since an Acknowledgement Receipt is always the full amount for one categorized purpose, matching the client's own paper form). New: `AcknowledgementReceiptsService.findOne()` now also fetches and returns `enterprise` (`companyLegalName`/`companyTradingName`/`address`, same select shape `ArInvoicesService.getDocument()` uses) merged directly onto the receipt response, rather than a separate document-envelope endpoint — verified against the real dev DB to return "NIG MARKETING CORPORATION" / "#32 NIG BLDG. MABINI ST. ILOILO CITY" exactly matching the shared reference. The account-table's single line reads "`<Account or Miscellaneous Collections>` — `<Payer Name>`", and "Reference" falls back to the system `number` when the cashier didn't type one, same fallback `buildCollectionReceiptHtml` already uses.
9. **A second "Collection Receipt" on-screen sheet, deliberately NOT wired into cash reconciliation, both downloading real .pdf files.** Developer asked whether an Acknowledgement Receipt "should also have a corresponding collections receipt." Investigated first: confirmed a real, structurally-identical gap to one already fixed for `CollectionReceipt` (Scenario 53 Part 5b) — `CollectionReceipt.posSessionId` lets a counter cash collection count toward `SessionsService.computeExpectedCash()` and the Daily Collection Report (`daily-collection.service.ts`), but `AcknowledgementReceipt` has no such field, so a cash Acknowledgement Receipt taken during a session would show as an unexplained drawer overage and be silently missing from the day's cash-in ledger. Developer's call after hearing this: explicitly declined the reconciliation wiring — "we just need a printed version... this is manual for a reason." The detail page's sheet markup was pulled into a reusable `ReceiptSheet` component and renders **twice on-screen**, stacked (Acknowledgement Receipt, then Collection Receipt directly below it). Both action buttons then became real `.pdf` downloads ("both should download a .pdf file") — this app's usual `window.open()`+`window.print()` "Save as PDF" pattern was replaced with `downloadElementAsPdf()` (`src/libs/print/htmlToPdf.ts`, already used by Purchase Orders' own Download button — `jspdf`+`html2canvas-pro`, captures the already-on-screen sheet via a ref), and the now-fully-unused `buildAcknowledgementReceiptHtml()`/`printAcknowledgementReceiptDocument()`/`printAcknowledgementReceiptAsCollectionReceiptDocument()` were deleted outright rather than left dead. Still not a real `CollectionReceipt` database row (this data has no `customerId`/`arInvoiceId` to satisfy that model) and still not part of any session/reconciliation flow.
