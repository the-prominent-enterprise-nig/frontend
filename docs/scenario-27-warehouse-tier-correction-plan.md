# Scenario 27 — Warehouse Tier Correction: Procurement → Warehouse → Branch Distribution — Gap Analysis & Closing Plan

Source: client correction, 2026-08-11 (not from either scenario source PDF — surfaced live during a planning conversation, same as Scenarios 21-26). No ClickUp tickets exist for this yet — new gap, not sourced from an existing sprint backlog.

## The scenario we're building toward

The client corrected a standing assumption: there are only **2 real warehouses**, not one per branch. The 41 are branches. The real flow:

1. Main Office requests stock from a supplier.
2. The supplier delivers it to one of the 2 real warehouses.
3. The warehouse distributes stock down to branches — either **pushed** by warehouse staff once stock arrives, or **pulled** by a branch requesting directly from a warehouse.
4. Branch ↔ Branch transfer is a separate, already-correct flow and stays exactly as it is — not in scope here.

Decisions already made in the 2026-08-11 planning conversation:

- The branch split is decided **at the warehouse, after stock physically arrives** — not pre-allocated by Main Office at request time.
- The **existing Stock Controller role** operates the warehouse tier too (assigned to a warehouse instead of/in addition to a branch) — no new persona, and no new dedicated "assigned warehouse" field either; reuse/extend whatever already scopes a Stock Controller to a branch.
- **Branches can request directly from a warehouse** (pull) — restocking is not push-only.
- The 2 warehouses are **PANAY** and **NEGROS**, fully standalone (`branchId: null` — not attached to any branch record, not even a head-office branch).
- **Regional pairing**: PANAY warehouse serves Panay-region branches, NEGROS warehouse serves Negros-region branches. Default behavior should route a branch to its own region's warehouse automatically, but **allow manual override** to the other warehouse (e.g. covering a stockout) rather than hard-blocking it.
- **Hard cap on requests, no partial fulfillment to design around**: a branch cannot submit a pull request exceeding the warehouse's live on-hand stock — the system must prevent over-requesting outright, not accept it and partially fill it.
- **This is a fully separate flow from Branch↔Branch Transfers**, not an extension of the existing Transfer screen/picker — different actors (Head Office, warehouse Stock Controller, branch Stock Controller), different operational shape, kept visually and functionally distinct from branch-to-branch transfers.

## What's already done (real building blocks)

1. **`Warehouse` and `Branch` are already distinct models.** `Warehouse` (`schema.prisma:3449-3483`) has only a soft FK `branchId` (line 3454, the codebase's `// FK*` convention — no Prisma relation, no `@@unique` on it at line 3480, and no FK constraint at the raw SQL level either, confirmed in `prisma/migrations/20260513120000_add_inventory_module/migration.sql:140-152`). No schema/migration change is required to support 2 warehouses ≠ 41 branches — only application code and seed data assume 1:1.
2. **`StockTransfer` is already warehouse-native.** `fromWarehouseId`/`toWarehouseId` (not `branchId`), full `create → dispatch → receive` lifecycle in `transfers.service.ts`. This is the natural extension point for warehouse-involving stock movement, not a new mechanism to invent.
3. **Goods receiving already lands stock on a warehouse, never a branch.** `GoodsReceipt` (`schema.prisma:4264-4302`) has only `warehouseId` (required, lines 4268-4269) — no `branchId` field exists on it at all. `PurchaseOrder` (`schema.prisma:4179-4218`) already carries `branchId` (requesting branch, used only for quota — `purchase-order.service.ts:465`) and `warehouseId` (delivery destination) as two separate fields.
4. **Standalone Warehouse admin CRUD already exists** (`inventory/warehouses/` frontend, `warehouses.controller.ts`/`.service.ts` backend) and already supports creating real warehouse rows without a branch. It was deliberately left alone by the 2026-08-10 relabel — **but as of Part 1 (2026-08-11) it's since been filtered to show only the 2 real warehouses**, see Closing Gap 1's status note below.
5. **A raw, un-relabeled warehouse picker already exists as a template.** The manual (non-PO) goods-receiving modal, `ReceiveStockModal.tsx:312-328`, shows a plain "Destination Warehouse" dropdown (`wh.code — wh.name`) with no branch-label swap — this is what the PO-receiving picker needs to go back to.

## What's not done / gaps

1. **Seed data hard-codes 1 warehouse per branch, not 2 real warehouses.** `prisma/seed.ts` creates exactly 41 `Warehouse` rows, one per branch (`branchId: branch.id`, name `"{branch.name} Warehouse"`, code `WH-##`, ~lines 4966-4977; console log literally prints "Warehouses: 41 (one per branch, status: active)"). Live dev DB confirms 41 branches / 41 warehouses, every warehouse linked to exactly one distinct branch, zero unlinked warehouses — there is no warehouse row anywhere that represents a real, branch-independent physical warehouse. Several later seed sections re-derive the same 1:1 assumption (~lines 5821-5824, 7002-7009, 7381-7384).
2. **`resolveWarehouseIdForBranch()` hard-assumes exactly one active warehouse per branch.** `warehouses.service.ts:24-62`, assumption stated explicitly in its own comment (lines 34-37). Called from `pos-inventory.service.ts`, `catalog.service.ts`, `service-drafts.service.ts`, `transactions.service.ts` (POS sale stock deduction), `serial-numbers.service.ts`, and `transfers.controller.ts` — i.e. nearly every stock-consuming surface in the app. This must keep resolving correctly for branch-local/sellable stock even once 2 independent real warehouses exist alongside it.
3. **PO/goods-receiving destination picker is labeled "Branch," not "Warehouse."** `ReceiveAgainstPoModal.tsx` — "Destination Branch" label (line 235), lock-when-single-warehouse logic (lines 83-90, 241-248) — and the display-only label in `PoDetailModal.tsx:96`. Both need to go back to real warehouse language, limited to the 2 real warehouses.
4. **No warehouse→branch distribution mechanism exists at all, push or pull.** Confirmed by repo-wide search for distribution/allocation logic — nothing matches. The only stock-movement mechanism between two inventory-bearing nodes today is `StockTransfer`, which this scenario keeps reserved for branch↔branch — the new warehouse↔branch flow needs its own mechanism, not a repurposing of `StockTransfer`.
5. **No live warehouse-stock visibility or request-cap enforcement anywhere.** Needed now that real scarcity exists (2 warehouses serving 41 branches) — the old fictional 1-warehouse-per-branch world never had contention, so nothing today checks a request against actual on-hand stock.
6. **`Branch` has no region/island field.** Confirmed in `schema.prisma:187-229` — only free-text `city`, no structured province/region/island field. There is currently no system-level way to know a branch is "in Panay" vs "in Negros," which the default-warehouse-routing decision above depends on.

## Closing the gaps

Sequenced — later steps build on earlier ones.

### 1. Introduce PANAY and NEGROS without breaking branch-local stock

**Problem**: seed data conflates "a branch's own sellable stock location" with "warehouse row," and `resolveWarehouseIdForBranch()`'s one-warehouse-per-branch assumption is load-bearing across POS/catalog/serials.
**Fix**: keep each branch's existing shadow warehouse exactly as-is — it continues to represent that branch's own local/sellable stock, so POS, catalog, and branch stock views need zero changes. Add 2 new `Warehouse` rows, PANAY and NEGROS, both `branchId: null`. `resolveWarehouseIdForBranch()` keeps resolving a branch's own local warehouse exactly as today — untouched.

**Status (2026-08-11, done, revised twice — see below):** `Warehouse.region` field + migration added, e2e-tested (`test/inventory-real-warehouses.e2e-spec.ts`).

**Addendum 1 (same day, during manual testing):** the client clarified that the 41 branch-local stock rows must never be _presented_ as "warehouses" anywhere, including the Warehouses admin page — that page previously listed all rows unfiltered. Added a `standaloneOnly` filter to `WarehouseFilterDto`/`findAllWarehouses` (takes precedence over branch-scoping, since a real warehouse belongs to no branch) and wired the admin page to always pass it. The manual (non-PO) goods-receiving "Destination Warehouse" picker (`ReceiveStockModal.tsx`) has the same problem but shares its data hook with an unrelated history-filter dropdown that legitimately needs branch-shadow warehouses too — deferred to Closing Gap 3, which already covers goods-receiving destination pickers.

**Addendum 2 (same day, superseding the original approach):** while manually testing, spotted that 2 of the 41 seeded branches are literally named `NWHSE` (Bacolod City) and `PWHSE` (Iloilo City) — confirmed with the client these ARE the 2 real warehouses, just seeded as ordinary branches because the seed loop never special-cased them. This means the original approach (2 brand-new standalone `Warehouse` rows, PANAY/NEGROS, created from scratch) produced **duplicates** of what should have been NWHSE's and PWHSE's own warehouses promoted instead. Reworked:

- Deleted the 2 duplicate standalone rows (schema/seed.ts and the live dev DB, including their opening stock/ledger).

- Net effect: `Branch` table still holds 41 rows, but only 39 are real operational branches; 2 are tagged `type: warehouse` and their warehouses are now PANAY/NEGROS.
- Deliberately not yet done: nothing filters `type: warehouse` branches out of ordinary branch pickers elsewhere in the app (POS terminal assignment, branch dropdowns, etc.) — that's real Part 4 territory once branch-vs-warehouse routing actually matters, not a Part 1 concern.

New Playwright spec `e2e/inventory-warehouse-branch-labels.spec.ts` covers the Stock page case as representative coverage (not one spec per file, given it's the same 1-line class of fix repeated). **Deliberately excluded**: `ReceiveStockModal.tsx`'s own "Destination Warehouse" picker (same file, different picker) — that one needs _limiting_ to the 2 real warehouses, not relabeling to show all 41 — already Closing Gap 3's job, left there.

**Fix**: add a region/island field to `Branch` (e.g. an enum of `panay`/`negros`), backfilled for all 41 existing branches. Derive "this branch's home warehouse" from that field (PANAY region → PANAY warehouse, and vice versa) — a new resolution function alongside the existing `resolveWarehouseIdForBranch()`, not a replacement for it.

**Status (2026-08-12, done):** `Branch.region` field + migration added, reusing the `Region` enum from Part 1. Backfilled all 41 branches (19 negros, 22 panay, including NWHSE/PWHSE themselves) — turned out the seed data's branch definitions already had explicit `// ── NEGROS ── / // ── PANAY ──` section comments and N-/P- prefixed codes marking exactly which branch is which, so this was a mechanical classification, not a geographic guess. `seed.ts`'s branch definitions and creation logic updated for fresh seeds; live dev DB backfilled directly (branch code prefix, with 3 explicit name-based overrides for the branches seeded with no code at all: Tanjay, Guimaras - Buenavista, Guimaras - Jordan). ### 4. Build a new, separate Warehouse↔Branch request/delivery flow

**Problem**: no mechanism moves stock between a real warehouse and a branch, in either direction — and per the 2026-08-11 decision, this must NOT be folded into the existing branch-to-branch Transfer screen.
**Fix**: a new inventory section, distinct from Transfers (proposed name TBD — "Warehouse Requests," "Branch Restock," open to whatever reads best to the client). Two entry points into what is functionally one relationship: a branch creates a **request** (warehouse defaults to the branch's own region per gap 2, overridable to the other warehouse), or a warehouse's Stock Controller creates a **delivery** to a branch after stock arrives. Both should probably share one underlying record/lifecycle (request → approve → dispatch → receive, similar shape to the existing Transfer lifecycle for familiarity) even though the entry screens differ — worth confirming this "one record, two entry points" structure before building (see Open Questions).

**Status (2026-08-12, all of Part 4 done — backend "4a", branch-side frontend "4b", warehouse-side frontend "4c"):** Named "Warehouse Requests" (client's choice). New, fully separate `WarehouseRequest`/`WarehouseRequestLine` models — not an extension of `StockTransfer`, matching the "fully separate" decision at the data layer too. Lighter lifecycle than Transfer's (no manager/HQ approval layers, since those don't apply here): `requested → ready (accept) / rejected (reject) → in_transit (dispatch) → received`. A **pull** (branch-initiated) starts at `requested`; a **push** (warehouse-initiated) starts directly at `ready` (creator is already the approver of their own delivery, so there's no separate accept step). `direction: pull | push` on the record, one lifecycle either way. `cancel` allowed by either side before dispatch.

Confirmed with the developer 2026-08-12: **Head Office can also create a pull request** (not branch-only) — mirrors the existing PO-creation pattern (`CreatePoModal.tsx`'s `currentUserBranchId ? <implicit own branch> : <explicit branch picker>`): a branch-scoped caller's own branch is used automatically; an unrestricted (Head Office) caller must pick an explicit `branchId`. Same rule for who can create a `push` — but a push's `branchId` (which branch it's going to) is always explicit, regardless of caller, since the warehouse-side actor's own branch never implies the delivery destination.

**Who can act on a warehouse's queue** (the earlier open question): implemented as region-matching, not a new "assigned warehouse" field — any Stock Controller whose own branch's `region` matches the warehouse's `region` can accept/reject/dispatch that warehouse's queue. `receive` stays exact-branch-only (region match isn't enough — grants visibility, not the receive action itself).

**Hard cap** (Closing Gap 5, folded into this part rather than built separately): checked at creation (a pull or push line item can't exceed the warehouse's live available stock, summed across every `StockBalance` row for that item — not a blind single-row check, so a batch-split item is still counted correctly) and re-checked at dispatch (stock may have moved since accept — dispatch just fails cleanly if so, no partial dispatch, matching "no partial fulfillment"). `StockBalance` decrement/credit uses a proper multi-row consume/credit helper, not a blind `updateMany`, which would have over-decremented if an item ever has more than one balance row for the same warehouse.

Backend permission catalog: 7 new rows (`inventory:warehouse-requests:{read,create,accept,reject,dispatch,receive,cancel}`), mirroring exactly how `inventory:transfers:*` was seeded — functionally redundant for Business Owner/Branch Manager/Stock Controller (all already hold the `inventory:*:*` wildcard, so these work with zero seed changes) but added anyway for admin-UI listing/future narrower-role grants, matching this codebase's established convention.

New e2e: `test/inventory-warehouse-requests.e2e-spec.ts`, 8/8 passing — full pull lifecycle, full push lifecycle, reject, hard cap rejection, region-scoping (visibility hidden via 404 for a wrong-region actor, matching Transfer's own "404 not 403 hides existence" convention), branch-scoping (visible-but-not-receivable for a same-region-different-branch actor, 403), Head-Office-explicit-branch creation, cancel.

**Deliberately not built in this pass**: partial receiving (Transfer has it; kept V1 simple — full receive only), a `GoodsReceipt` document on receive (Transfer's receive creates one for audit-trail parity; skipped here to avoid pulling in GL-posting scope), and no region restriction on a _push_'s destination branch (a warehouse can push to any branch, not just its own region's — the region rule is specifically about which warehouse a branch defaults to when _pulling_).

### 5. Enforce the request cap against live warehouse stock — folded into Closing Gap 4 above, done as part of it

**Addendum (2026-08-12) — existing catalog data didn't actually match "every item is serial-tracked."** All of Part 5's serial-correctness work (5a/5b/5c) only holds for items where `isSerialTracked` is true. Testing the real receive flow surfaced that most of NIG's seeded catalog had it false, so there was nowhere to input a serial at all. Client confirmed the rule: every real physical product is serial-tracked, no exceptions; services/parts/consumable-bundle rows are the only legitimate non-serial items.

Scoped to 7 items confirmed as real physical products with no other blast radius (`Universal Remote Control` deliberately excluded — it's a load-bearing fixture across 16 existing e2e specs, left non-serial-tracked to avoid destabilizing unrelated suites): LED Bulb 9W (2-pack), Extension Cord 3-Outlet 3m, Refrigerator Deodorizer, Aircon & Appliance Cleaning Spray, TV Stand, Side Cabinet, Electric Stand Fan.

Investigation found 6 of the 7 had been seeded at a uniform 200 units per location (41 branch-local rows + WH-NEGROS + WH-PANAY ≈ 43 locations each) — fabricating matching serials at that scale would have meant ~48,000 placeholder `SerialNumber` rows across just these 6 items, which the client flagged as making seeding too slow for a baseline that's meant to be a dev/demo starting point, not a real inventory count. Client's call: bring every location down to a lean 20-unit baseline first, then fabricate exactly matching serials on top — real growth past that baseline should come from actually buying through the PR → PO → receive flow (which Closing Gap 3 just fixed to record serials properly on receipt), not more fabricated data.

Ran as a one-off script against the dev DB (not a `prisma/seed.ts` change — this corrects already-seeded state, doesn't change what a fresh seed produces): for each of the 7 items, set `isSerialTracked: true`; for every existing `StockBalance` row, reset to `onHandQty = availableQty = 20`, `reservedQty = 0`, and create exactly 20 matching `SerialNumber` rows (`status: in_stock`, `currentWarehouseId` set to that row's warehouse) labeled `AUTO-<sku>-<warehouse code>-<seq>` so they're clearly identifiable as fabricated baseline data, not real receiving history. Electric Stand Fan had zero existing stock anywhere, so instead of reducing anything it got a fresh 20-unit/20-serial starter batch seeded at just the 2 real warehouses (WH-NEGROS, WH-PANAY) — nothing at branch level, since there was never any to correct. Totals: 820 units/serials each for the 6 previously-200 items, 40 for Electric Stand Fan — 4940 `SerialNumber` rows total, verified against `StockBalance.onHandQty` sums post-run (exact match, no drift).

**Not done as part of this**: `prisma/seed.ts` itself still seeds these 7 items the old way (non-serial-tracked, 200/location) — a fresh environment seeded from scratch won't match this correction until the seed script is updated too. Flagged, not actioned — the client's instruction was scoped to "make seeding faster" for the _live_ dev DB, not necessarily a change to the seed script's own defaults; confirm with the client before touching `seed.ts` if fresh-environment parity matters.

## Retirement of Warehouse Request (2026-08-14)

Closing Gap 4's net-new "Warehouse Request" feature (Parts 4a-4c, 5a-5c, and a same-day driver/logistics dispatch capture) was built, shipped, and fully tested — then retired one day later. Client's observation: `StockTransfer`'s own warehouse picker already includes the 2 real warehouses (`fromWarehouseId`/`toWarehouseId` accept any `Warehouse` row, branch-local or standalone — it was always warehouse-native under the hood, per this doc's own "What's already done" section above), so a dedicated warehouse↔branch mechanism was redundant with what Transfer could already do, once a few gaps were closed.

**Before retiring, ported the 3 things Warehouse Request had that Transfer didn't** — scoped so they only activate when one endpoint is a real standalone warehouse (`branchId: null`), leaving ordinary branch↔branch transfers provably untouched (verified against all 7 existing Transfer e2e spec files, both backend and Playwright, before and after):

1. **Manager/HQ approval tiers skipped** for a warehouse-leg transfer — lands directly on `requested`. Deliberately does _not_ mirror Warehouse Request's own push self-approval (client's call, 2026-08-14): every warehouse-leg transfer still needs an explicit accept step, no self-approval path.
2. **Region-based warehouse-side authorization** — `assertWarehouseScope()` (renamed from `assertWarehouseBranchScope()`) falls back to region match when the relevant warehouse has no branch owner, since exact branch-ownership can never be satisfied for one. Also fixes a real, previously-undiscovered bug: before this, _any_ branch-scoped actor got a 403 trying to act on a transfer touching a real warehouse, since `branchId !== actorBranchId` is always true when `branchId` is `null`. Extended to `findAll`/`findOne`'s visibility scoping too (not just the 5 action endpoints) — otherwise a region-matched actor would be authorized to act but unable to even see the record.
3. **Live per-serial re-check at dispatch** — added to `dispatch()`, applies universally (not just warehouse-leg transfers), closing a real gap: Transfer's dispatch never re-verified a specific serial was still available right before consuming it, unlike Warehouse Request's own dispatch which already did.

New coverage: `test/stock-transfer-warehouse-leg.e2e-spec.ts`, 4/4, covering all 3 behaviors plus a full create→accept→dispatch→receive lifecycle for a warehouse-leg transfer. Frontend wired to match (`TransferList.tsx`/`TransferDetailModal.tsx` now compute `currentUserRegion` the same way Warehouse Request's UI did, so the action buttons actually render for a region-matched actor — backend authorization alone isn't enough if the UI never shows the button).

**Removed**, backend: `warehouse-requests.{controller,service,dto}.ts`, the `WarehouseRequest`/`WarehouseRequestLine` models and `WarehouseRequestDirection`/`WarehouseRequestStatus` enums (migration `20260814062707_remove_warehouse_requests` — a genuine `DROP TABLE`, 13 rows of real test data each, both tables), `inventory.module.ts` registrations, 7 permission-catalog rows in `prisma/seed.ts` (plus its now-invalid `warehouseRequest*.deleteMany()` cleanup calls), `test/inventory-warehouse-requests.e2e-spec.ts` (16 tests). Frontend: the whole `/inventory/warehouse-requests` route + `_components`/`_hooks`/`_actions`, `src/schema/inventory/warehouse-requests/`, the SideBar nav entry and dashboard quick-link, `WAREHOUSE_REQUESTS_*` permission constants, `e2e/inventory-warehouse-requests.spec.ts` (7 tests) and its 4 now-unused `e2e/utils.ts` helpers. `get-branches.ts` (a small generic branch-lookup action Transfer's own region logic now depends on too) was moved into `transfers/_actions/` rather than deleted, since Transfer needed it independently.

Verified zero regressions from the removal itself: re-ran the full existing Transfer suite (backend 7 files + frontend 3 Playwright specs) after removal — every failure present is byte-identical to a pre-removal baseline run (2 pre-existing backend failures across accept-reject/partial-receipt, 1 in hq-approval, 21 in repair-transfer's own unrelated setup bug; 8 pre-existing frontend Playwright failures from dev-DB/fixture drift unrelated to this work) — confirmed via direct stash-and-compare on the original code, not assumed.
