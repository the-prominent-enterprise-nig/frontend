## The scenario we're building toward

A warehouse clerk finds defective stock, agrees a return with the supplier, and raises a debit memo. Their side approves and finalizes it; accounting receives the finished document.

1. The clerk opens **Inventory → Debit Memos**, raises a draft naming the supplier, the invoice to deduct against, and the items going back — with COA account, quantity, unit price, tax code and tax amount per line.
2. They type the supplier's DR number and attach a photo of the waybill.
3. Nothing has touched the general ledger, the AP bill, or stock on hand. The memo is a draft.
4. Their supervisor approves it, then finalizes it. Only on finalize does stock leave, the journal entry post, and the bill's outstanding balance drop.
5. **Accounting now sees it** — and only now. Their screen is read-only and lists finalized memos.
6. The AP bill's row links through to the memos applied against that invoice.

**Result**: the money side of a defective return is an auditable document with a signature trail, not a one-shot dialog buried in an unrelated screen.

## Decisions taken

Confirmed with the developer before building:

1. **Keep the existing Inventory Returns tab.** Debit Memos is added as a separate screen; nothing is removed.
2. **Two separate records**, not one model with a type flag — an inventory-moving supplier debit memo, and a separate accounting-only adjustment memo for support/sponsorship. The latter is **generated by accounting**, raised in the Accounting module, and never has an inventory side.
3. **Lifecycle is Draft → Approved → Final.**
4. **Deduct against any SI**, not necessarily the one the damaged unit was invoiced on.
5. **Debit Memos is its own sidebar entry under Inventory**, not a tab inside the Stock Transfers hub.
6. **Accounting does not approve.** The whole draft → approve → finalize lifecycle belongs to the Inventory side — the people who agree the return with the supplier. Accounting is a _consumer_: its screen is read-only and defaults to showing only FINAL memos. That is the literal reading of "debit memo should be final to be available for accounting".

## What's already done ✅

1. **`SupplierDebitMemo` exists and works** — `backend/prisma/schema.prisma:1295-1320`, service at `backend/src/accounting/supplier-debit-memos/supplier-debit-memos.service.ts`. `issue()` writes a `StockLedger` row (`supplier_return`, negative qty), decrements `StockBalance`, posts `Dr AP_PAYABLE / Cr INVENTORY_ASSET`, and increases `APBill.amountPaid` as a non-cash settlement. `void()` reverses all of it. Routes and permissions are seeded (`prisma/seed.ts:2012-2027`).
2. **`APBill.billNumber` is already the supplier's SI number** (`schema.prisma:1187-1198`), unique per `(supplierId, billNumber)` — so "link the memo to a purchase invoice" is half-modelled through the existing required `apBillId`.
3. **`APBill.debitMemos` back-relation exists** (`schema.prisma:1266`) — the client's "record that a debit memo was used for a certain invoice" needs no new structure, only surfacing.
4. **Attachments need no schema work.** `File` + `FileAttachment` (`schema.prisma:6704-6745`) are polymorphic on `entityType`/`entityId`. `ap-bills/_actions/upload-voucher-attachment.ts` + `VoucherPanel.tsx` are a working precedent to copy.
5. **The support/sponsorship accounts are already in the chart** — `4-09-023 "Support from Supplier"` (`coa-seed.service.ts:614-620`) and `4-09-012 "Incentives from Supplier"` (`:536-542`), both seeded REVENUE accounts under Other Income, both unmapped, nothing posting to them.
6. **`PermissionsGuard` is OR-semantics** (`auth/gaurds/permission.gaurd.ts:47` — `requiredPermissions.some(...)`), so one route can accept either an accounting or a warehouse permission with no new machinery.

## What's not done / gaps ❌⚠️

1. **Single-item memos.** No line table. One memo = one item + one warehouse + one quantity. The client's spec lists COA account, quantity, unit price, tax code and tax amount _per line_.
2. **No lifecycle.** `SupplierDebitMemoStatus` is `ISSUED | VOID` only. There is no draft, no approval, and therefore no way to honour "debit memo should be final to be available for accounting" — today it is live the instant it is created.
3. **No list page, no sidebar entry, no void UI.** The only surface is `SupplierDebitMemoDialog.tsx` (179 lines), launched from an `Undo2` button in `APBillsList.tsx:229-239`. `SupplierDebitMemos.list/get/void` exist in `AccountingV2Data.ts:1000-1013` and are **never called** — dead code.
4. **No inventory surface at all.** A warehouse clerk cannot raise a return; it can only be done from Accounting → AP Bills.
5. **No DR field and no attachment.** The word "waybill" appears nowhere in either repo.
6. **No `tenantId` column.** Tenant scoping runs through `item.tenantId` — which evaporates the moment a memo has no inventory line.
7. **The journal entry is not atomic with the stock writes.** `supplier-debit-memos.service.ts:237,266` post with the outer `this.prisma` rather than the transaction client, so a late failure can orphan a journal entry.
8. **The dialog violates the project's own form convention** — raw `useState` instead of react-hook-form + zodResolver + `Controller`.
9. **No accounting-only adjustment memo** for support/sponsorship. Nothing can express a supplier deduction that doesn't move stock.

### Known-wrong GL behaviour (pre-existing, deliberately out of scope for Part 1)

Each of these changes GL output for future memos, so each needs its own sign-off rather than being quietly corrected:

1. **Inventory is credited at the negotiated amount, not at cost.** No `StockCostLayer` is consumed. Negotiate ₱10,000 back on units carried at ₱8,500 FIFO and inventory is over-credited by ₱1,500 — the balance sheet drifts from the stock ledger.
2. **Input VAT is never reversed.** Returning goods reduces a VATable purchase, so the input VAT claimed at `APBill.receive()` should come back out.
3. **`branchId` is never set on the journal entry**, though `posting.post()` accepts one and the memo's warehouse knows its branch.

## Closing the gaps

### Part 1 — The memo becomes a real document

**Schema.** New `SupplierDebitMemoLine` following `BusinessExpenseLine`'s shape (COA account + amount + taxCode + taxAmount), extended with `quantity`/`unitPrice`/`lineTotal` and an optional `serialNumberId`. `itemId`/`quantity` move off the header; `warehouseId` stays (one physical shipment leaves one warehouse). Header gains `tenantId`, `deliveryReceiptNumber`, `subtotal`/`taxAmount`, and six lifecycle audit columns. `memoNumber` becomes unique per tenant.

**The SI question — two invoices, one enforced.** The notes' apparent contradiction is two different invoices:

| Reference                              | Where            | Meaning                                                                                                              | Enforced                                                              |
| -------------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `apBillId`                             | header, required | The SI the debit is **applied against** — the bill whose balance drops. Free choice among the supplier's open bills. | **Yes** — must be `RECEIVED`/`PARTIAL`/`OVERDUE`, total ≤ outstanding |
| `SupplierDebitMemoLine.sourceApBillId` | line, nullable   | The SI the unit **originally came in on** — provenance. Auto-suggested, overridable, blankable.                      | **No**                                                                |

`sourceGoodsReceiptId` sits alongside it, giving the RR number to print — the notes' "RR to branch → RR to warehouse → debit memo" chain.

**Tradeoff, stated plainly**: there is no consumption ledger against `sourceApBillId`, so nothing stops one defective unit being cited on two memos against two bills. That is the accepted cost of free settlement choice. The guards that protect the books are elsewhere and _are_ enforced — cannot return more than is on hand, cannot debit more than is owed.

**Lifecycle.** `DRAFT` (editable, no GL) → `APPROVED` (locked, still no GL) → `FINAL` (posts JE, moves stock, reduces bill) → `VOID`. Void from DRAFT/APPROVED reverses nothing; from FINAL it reverses everything. `APPROVED` is not un-approvable — if a change is needed, void and re-create, so an approval signature can never be silently invalidated.

`ISSUED` migrates to `FINAL`: such a row has already posted, already moved stock, already reduced the bill, which is exactly what `FINAL` means.

**Service.** `issue()` splits into `create`/`update` (draft only), `approve`, `finalize`, `void`. The atomicity fix is two changes, not one — pass `tx` to `posting.post()` in finalize, **and** add an optional `tx` param to `posting.reverse()` (`posting.service.ts:335`, which currently accepts none) for void.

**Frontend.** A standalone route at `/inventory/debit-memos` with its own sidebar entry under Inventory (between Stock Transfers and Suppliers) — not a tab in the Operations hub. It carries the full lifecycle: raise a draft, edit it, attach the waybill, approve, finalize, void.

The Accounting screen at `/accounting/supplier-debit-memos` is **read-only** and defaults its status filter to FINAL. Every route accepts an Inventory permission alongside the Accounting one (`PermissionsGuard` is OR-semantics), so the split is enforced by permission grants rather than by hidden buttons.

The three sidebar memo entries are named to disambiguate: "Customer Credit Memos", "Customer Debit Memos" (both AR) and "Supplier Debit Memos" (AP).

`SupplierDebitMemoDialog.tsx` is retired; the AP bill's `Undo2` button becomes a link to that bill's finalized memos.

### Part 2 — Accounting-generated support/sponsorship memo

New `SupplierAdjustmentMemo` + lines, same lifecycle, structurally incapable of moving stock (no `itemId`, no `warehouseId`, no `StockLedger` write anywhere in its service). New mapping key `SUPPLIER_SUPPORT_INCOME` pointed at the already-seeded `4-09-023`.

Three files per mapping key, not two: `MAPPING_KEYS` in `posting.service.ts`, `STANDARD_MAPPINGS` in `account-mapping.service.ts`, and a `mappingKey` on the `coa-seed.service.ts` entry — `seedPH()` re-maps existing accounts, so re-running the seed wires it up on live tenants with no data migration.

## Open questions

Three of these are for the client's **accountant**, not the ops lead who wrote the notes:

1. **Does the adjustment memo require an AP bill, or can it stand alone?** The notes say both — _"allow insertion for support/sponsorship in AP"_ vs _"debit/credit is a standalone"_. Recommendation: require `apBillId`, reading "standalone" as "its own document type with its own JE", which is already true.
2. **Is the line's tax amount meant to reverse input VAT, or is it print-only?** It should reverse — but that changes the VAT return for every future memo.
3. **Is supplier support REVENUE or contra-COGS?** The seeded COA says REVENUE, so honour it — but flag that it inflates topline.
4. **`feat/scenario-18-returns-exchanges-disposition`** (`b91c9df`, both repos) — 1 commit ahead, 131 behind. Land, rebase, or abandon? It touches returns disposition and will conflict.

## Risks

**Biggest**: the status enum swap rewrites the status column on every existing row. `ALTER TYPE … ADD VALUE` cannot be used in the migration that then uses the new value (Prisma wraps each in one transaction), so this needs the create-cast-drop-rename form. Snapshot `supplier_debit_memos` first and run `SELECT status, count(*) … GROUP BY 1` before and after as reconciliation.

**Second**: Part 1 drops `itemId`/`quantity` from the header. Grep found exactly one backend file referencing the model — but re-run that grep against `test/` and any reporting layer outside `src/` before merging.

The header→lines migration has an exact in-repo precedent to copy: `prisma/migrations/20260831150500_scenario_40_part6_multiline_expense/migration.sql` creates the line table, `INSERT … SELECT`s one line per existing header, then drops the old columns — all in one file.
