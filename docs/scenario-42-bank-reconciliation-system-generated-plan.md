# Scenario 42 — Bank Reconciliation: System-Generated Pending Items — Gap Analysis & Closing Plan

Source: developer request, 2026-09-01, prompted by the client's own "Bank Reconciliation" workbook (sample PDF supplied live) — an itemized worksheet of pending deposits/withdrawals reconciling a BDO statement balance to the books, ending in a `RECONCILED` stamp at zero discrepancy. Bank reconciliation is already named as a target scenario in `module-scenarios.md:221` ("the accountant enters the statement balance and reconciles to zero") but has never had its own numbered plan doc — this is that doc.

## The scenario we're building toward

An Accountant opens **Accounting ▸ Bank Reconciliation**, picks a bank account and a statement date, and types in exactly one number by hand — the closing balance off the real BDO statement, the one figure that can never come from inside the system. Everything else the client's sample shows as a typed list, the system now generates: every AR collection, AP check payment, and clearing settlement already posted against that account, dated on or before the statement date, that hasn't already been confirmed cleared in an earlier reconciliation — laid out as Pending Deposits and Pending Withdrawals, each row carrying its own reference (OR/collection reference or CK# + payee, same shape as the client's `CRP#...` / `CK#...` lines) and amount.

The accountant works the real bank statement against that generated list, checking off which pending items actually appear as cleared on it (some won't — a check from three weeks ago may still be outstanding, and correctly stays pending into next month — **decided**: this stays a manual per-item confirmation, never an automatic "everything below the cutoff date counts as cleared" shortcut, since that would silently misstate genuinely outstanding items). As they check items, the worksheet recomputes live: Adjusted Balance = Statement Balance + confirmed-cleared deposits − confirmed-cleared withdrawals, compared against the System Balance the system now computes itself (from the account's GL cash balance as of the statement date, not typed in) — Discrepancy shows as they go, and the record can only be marked **Reconciled** once it's zero, matching the client's own `RECONCILED` stamp. Completing it clears only the checked items (so they drop off next month's pending list) and leaves everything unchecked genuinely outstanding, rolling forward automatically.

This worksheet is a **dedicated full page**, not a modal — there's simply too much on it (two itemized, checkable lists plus live-computed totals) to work in a dialog, and the screen already has precedent for exactly this: the "Fund Transfer" button next to "New Reconciliation" already routes to its own page (`/accounting/bank-reconciliation/transfer`) rather than opening a dialog. "New Reconciliation" follows the same pattern — it navigates to `/accounting/bank-reconciliation/new` to pick the account/date/statement balance, then on save routes to `/accounting/bank-reconciliation/[id]`, the worksheet itself. That `[id]` page is also where a click on any row in the reconciliations table should land — today the list rows aren't clickable at all, only the inline Complete checkmark does anything.

**Decided**: POS ▸ Cash-in-Transit stays its own page — it's a branch cashier's day-to-day task (clear today's closed sessions), gated by a branch-scoped permission, on a completely different cadence from an Accountant's monthly whole-account reconciliation. Folding the two together would either give branch staff bank-rec access they shouldn't have, or turn the Accountant into a bottleneck for routine daily cash sweeps.

**Superseded during implementation (2026-09-01)**: the original intent was for the worksheet to at least _read_ `PosSession.citClearedAt` read-only, alongside the checkable AR/AP/transfer/settlement lines. Re-verifying the schema while building Part 1 found `PosSession` has **no `bankAccountId` at all** — `clearCashInTransit()` lets the accountant pick any bank account at clearing time, so an uncleared session isn't actually attributable to one specific bank account in advance. Showing it in every account's worksheet would double-count the same uncleared cash everywhere; showing it in none loses the visibility this was meant to add. Decided: **drop cash-in-transit visibility from this scenario entirely** rather than guess. Closing this properly needs its own small follow-up first (e.g. a default deposit account per branch/terminal) — see "Not in scope" below.

**Also superseded during implementation (2026-09-01)**: "Fund Transfer" (`transfer()`, `bank-accounts.service.ts:196-266`) turned out to have **no persisted model of its own** — it posts a `JournalEntry` directly and moves both accounts' `currentBalance`, with nothing in the database representing "this specific transfer" to attach a `clearedAt` flag to. Adding one would mean introducing a real `FundTransfer` model as new surface area on an existing, already-working feature — a bigger, separate change than this scenario originally scoped. Decided: **drop Fund Transfers from this scenario too**, same reasoning as cash-in-transit above.

## What's already done ✅

1. `BusinessBankAccount` / `BankReconciliation` (`schema.prisma:1424`, `:1512`) and the accounting-side `bank-accounts` module already own the reconciliation record, its list/create/complete endpoints, and the **Accounting ▸ Bank Reconciliation** screen (`BankRecon.tsx`) — the page, the table, the permission gate (`accounting:bank-accounts:reconcile`), and the audit log entries on create/complete already exist. This doc extends that surface rather than building it from nothing.
2. The exact "generate candidates, let the user confirm which ones actually cleared, mark only those cleared" pattern this scenario needs **already exists**, just scoped to one transaction type: `PosSession.citClearedAt` (`schema.prisma:~2409`) + `BankAccountsService.clearCashInTransit()` (`bank-accounts.service.ts:276-330`) — a session only counts as pending cash-in-transit while `journalEntryId` is set and `citClearedAt` is null; the standalone **POS ▸ Cash-in-Transit** page (`pos/cash-in-transit/`) lets a user select sessions and clear them via a claim-then-act update (`updateMany` guarded by `citClearedAt: null`, so it can't double-clear). This is the template to extend to AR/AP payments, not a pattern to invent.
3. `ARPayment` and `APPayment` already carry `bankAccountId` (`schema.prisma:824`, `1223`) plus a per-payment reference (`ARPayment.reference`, `APPayment.chequeNumber`/`reference`) and `journalEntryId` — the raw data a "Pending Deposits/Withdrawals" list needs already exists per payment row, it's just never queried back out grouped by bank account.
4. `ClearingSettlement` (behind `ClearingSettlements`/`BankAdjusting` in `BankRecon.tsx`) already posts dated, bank-account-scoped GL movements with a real row per settlement — the same "list what's posted against this account since the last statement" query needs to fold it in too, and it's already structured consistently enough to do so. (`FundTransfer` looked like the same shape from the outside — it isn't; see the "Also superseded" note above.)

## What's not done / gaps ❌⚠️

1. **`BankReconciliation` has no line items at all.** `createReconciliation()` (`bank-accounts.service.ts:96-106`) just persists two flat, hand-typed numbers — `statementBalance` and `systemBalance` — plus free-text `notes`. Nothing links a reconciliation record back to the actual payments/transfers it's supposed to explain.
2. **"System Balance" is typed by a human, not computed.** No endpoint derives a bank account's book balance as of a given date from the GL — the accountant has to already know that number and type it in, defeating the point of a _system-generated_ reconciliation. The underlying mechanism isn't missing, though: `reports.service.ts`'s private `getAccountBalances(startDate, endDate, ...)` (`reports.service.ts:54-119`, already powering `trialBalance()`/`balanceSheet()`) sums posted `Transaction` rows up to an open-ended cutoff date exactly the way this needs — it just returns every account with no way to isolate one bank's GL cash account. This is a reuse-and-extend job (add an `accountId` filter, or filter its returned array), not a new balance query built from scratch.
3. **No "cleared" concept exists for AR/AP payments or clearing settlements** — only `PosSession` has it (`citClearedAt`, gap ✅2 above). Without an equivalent flag, the system has no way to know, item by item, which collections/check-payments already cleared in a prior reconciliation vs. are still genuinely outstanding.
4. **`bankAccountId` is optional and never enforced**, even though the field already exists in the UI on both sides — AR Invoices' "Record Payment" dialog (`ARInvoicesList.tsx:1968-1999`) has a "Source of Fund" bank-account select sitting right next to its payment-Method select, and AP Bills' "Record Payment" dialog (`APBillsList.tsx:462-475`) has the same "Source of Fund" select — both default to "— Not tracked —" and stay that way unless someone deliberately picks an account. A generated pending list is only as trustworthy as this being reliably filled in at the point of recording, not an afterthought at reconciliation time.
5. **The Complete action has no correctness gate.** `BankRecon.tsx:150-158`'s checkmark button calls `completeReconciliation()` unconditionally — an accountant can mark a reconciliation "Reconciled" while Statement Balance and System Balance still disagree; the UI only tints the difference amber, it doesn't block completion.
6. **No audit trail of _why_ two balances matched.** Today a completed reconciliation is two numbers and a boolean — a later reviewer (or an auditor) can't see which specific deposits/withdrawals were treated as outstanding, only the final totals.
7. **The Bank Reconciliation worksheet has no visibility into cash-in-transit at all** — **out of scope for this implementation**: `PosSession` has no `bankAccountId`, so an uncleared session can't be attributed to one specific bank account ahead of clearing time (see the "Superseded during implementation" note above). Left as a real, still-open gap for a future pass, not closed here.
8. **"New Reconciliation" is a modal (`ReconForm`, `BankRecon.tsx:454-573`).** A checkable, two-list itemized worksheet with live-computed totals doesn't fit a dialog — it needs to be its own page, the way `/accounting/bank-reconciliation/transfer` already is for Fund Transfer. Relatedly, reconciliation rows in the list table aren't clickable/linked to anything today, so there's no way to reopen an in-progress or completed reconciliation and see its detail.

## Closing the gaps

### 1. A `cleared` concept for AR/AP payments and clearing settlements, mirroring `PosSession.citClearedAt` — plus a persisted worksheet line table

**Fix**: add `clearedAt DateTime?` (and, for traceability, `clearedInReconciliationId String?` back to the `BankReconciliation` that cleared it) to `ARPayment`, `APPayment`, and `ClearingSettlement`. A row only counts as a pending _candidate_ for a given bank account while it has a `bankAccountId`, a `journalEntryId` (already posted to the GL — never surface an unposted draft as pending cash), and `clearedAt: null`.

**Decided**: checkbox state while the accountant works a worksheet is not held only in the browser until Complete — losing 20-40 checked items to a refresh or crash mid-session would be a bad enough experience to design around. A new `BankReconciliationLine` model (`bankReconciliationId`, `sourceType` enum `AR_PAYMENT | AP_PAYMENT | CLEARING_SETTLEMENT` — `POS_SESSION` and `FUND_TRANSFER` both dropped, see the "Superseded during implementation" notes above — `sourceId`, direction, amount/date/reference snapshot, `checked` boolean default `false`) is bulk-created once, the moment a reconciliation's worksheet is first opened — a snapshot of that moment's pending candidates. Each checkbox toggle is a small `PATCH` on one line, persisted immediately. This table also directly closes gap ❌6 (no audit trail): a completed reconciliation's full line-by-line detail — what was pending, what got checked, what didn't — is permanently queryable, not bolted on separately.

Completing a reconciliation (#4 below) reads which lines are `checked` from this table — rather than trusting a submitted array of IDs — and only then writes `clearedAt`/`clearedInReconciliationId` onto the real `ARPayment`/`APPayment`/`ClearingSettlement` rows, using the same claim-then-act `updateMany` guard `clearCashInTransit()` already uses so two accountants can't double-clear the same item.

### 2. Backend: compute System Balance, generate the worksheet lines, per bank account/statement date

**Fix**: `createReconciliation()` (`bank-accounts.service.ts:96-106`) extends to, in one transaction: (a) compute the book balance for that account's GL cash mapping as of `statementDate` by extending `reports.service.ts`'s existing `getAccountBalances()` (line 54-119, already used by `trialBalance`/`balanceSheet`) with an `accountId` filter rather than writing a new balance query, and (b) bulk-create the `BankReconciliationLine` rows from #1 — every `ARPayment`/`APPayment`/`ClearingSettlement` row scoped to that `bankAccountId`, dated on/before `statementDate`, with `clearedAt` null. A companion `GET /bank-accounts/reconciliations/:id` returns the reconciliation plus its lines, shaped into `pendingDeposits[]` / `pendingWithdrawals[]` (each with date, reference, source document link, amount, `checked`), matching the client sample's per-line shape. A `PATCH /bank-accounts/reconciliations/:id/lines/:lineId` toggles one line's `checked`.

### 3. Frontend: two new full pages, not a modal — closes gap ❌8

**Fix**: retire `ReconForm`'s modal (`BankRecon.tsx:454-573`) in favor of:

- `/accounting/bank-reconciliation/new` — a small page (Bank Account, Statement Date, the one still-typed **Statement Balance**) that on submit creates the `BankReconciliation` row + its lines (#2) and redirects into —
- `/accounting/bank-reconciliation/[id]` — the worksheet itself: Pending Deposits / Pending Withdrawals rendered as checkable line lists (unchecked = still outstanding, the safe default), each toggle firing the `PATCH` from #2 immediately, a live-computed Adjusted Balance and Discrepancy, and System Balance shown read-only (computed, not typed). This is also where an in-progress or already-completed reconciliation reopens to — checked state is exactly as the accountant left it.

The list table's rows link to `/accounting/bank-reconciliation/[id]` (they currently link nowhere), and "New Reconciliation" becomes a `Link`, matching how "Fund Transfer" already navigates rather than opening a dialog.

### 4. Complete = clear only what's checked, and gate it on zero discrepancy

**Fix**: `markReconciled()` stops just flipping a boolean — it re-reads which `BankReconciliationLine` rows are `checked`, persists the computed `systemBalance`/`discrepancy` onto the `BankReconciliation` row, sets `clearedAt`/`clearedInReconciliationId` on the real source row behind every checked line (leaving unchecked ones untouched so they roll forward into the next worksheet), and the frontend Complete button (`BankRecon.tsx:150-158` / the new `[id]` page) becomes disabled until `Math.abs(discrepancy) < 0.01`, closing gap ❌5.

### 5. Require `bankAccountId` at the point AR/AP payments are recorded

**Fix**: make "Source of Fund" required whenever the payment isn't plain cash, so gap ❌4 doesn't silently undermine the whole feature going forward. The two forms aren't symmetric, though, and this needs a real look during implementation rather than one shared rule: AR's `PaymentDialog` has its own Method select right there (`ARInvoicesList.tsx:1968-1999`), so "required when Method is CHECK/BANK_TRANSFER" is a direct, local condition. AP's `PayBill` dialog has **no payment-method selector of its own** — the bill's method/source-of-payment lives elsewhere on the bill — so the same conditional needs to read that field instead of one local to the dialog; confirm exactly where during implementation. (Existing rows with no `bankAccountId` stay as-is — not backfillable without guessing.)

## Not in scope for this doc

- Actually ingesting a real bank statement file (CSV/PDF parse-and-auto-match against pending items) — the accountant still manually checks items against the physical/PDF statement they're holding, same as the client's own workbook. Real statement import is a materially bigger feature (a bank feed/OFX integration) and not implied by the sample provided.
- Cash-in-transit visibility on the worksheet at all — descoped mid-implementation once `PosSession`'s lack of a `bankAccountId` surfaced (see the "Superseded during implementation" note above). A future pass needs to decide how to attribute an uncleared session to a specific bank account (e.g. a default deposit account per branch/terminal) before this can be added safely.
- Fund Transfer visibility on the worksheet at all — descoped mid-implementation once it turned out to have no persisted model to attach `clearedAt` to (see the "Also superseded" note above). A future pass would need to add a real `FundTransfer` model first, as its own separate change.
- Backfilling `bankAccountId` on historical AR/AP payment rows that never had one.
