# Scenario 56 — Employee Cash Loan: Disbursement Bank Field for Cash/Check & Post-Submission Editability — Gap Analysis & Closing Plan

**Source**: phone call from Ms Helie (client), 2026-09-21, relayed via a screenshot showing a Bank Transfer dropdown's bank list. An addendum to Scenario 52 (Employee Cash Loan on the POS Side, which this scenario's own model/posting logic builds directly on). The call raised three points; two are planned here, the third is called out below as explicitly out of scope for this doc.

## The scenario we're building toward

1. A cashier disbursing an Employee Cash Loan should be able to record a Bank / Cash Account regardless of disbursement method. Today that field only appears when Disbursement Method is Bank Transfer — Ms Helie wants it visible for Cash and Check too, so whichever bank shows up for a bank transfer also shows up for check and cash.
2. A submitted Employee Cash Loan should stay editable after issuance. Today the loan is create-only and permanently locked the moment it posts — no edit surface exists anywhere, backend or frontend.

## What's already done ✅

1. **The Bank / Cash Account field already exists and already works — just gated to one method.** [`NewLoanForm.tsx:239-250`](<../frontend/src/app/(app)/(dashboard)/pos/employee-cash-loans/new/_components/NewLoanForm.tsx#L239-L250>) only renders the field when `disbursementMethod === 'BANK_TRANSFER'`; the client-side `validate()` at line 100-103 only requires it for that same method. The DTO (`CreateEmployeeCashLoanDto.bankAccountId`, `backend/src/pos/employee-cash-loans/dto/employee-cash-loans.dto.ts:61-66`) is already `@IsOptional()` — nothing at the DTO level blocks sending it for Cash/Check today.
2. **The bank list itself is the real accounting bank register, not a curated short list.** `listBankAccounts()` (`employee-cash-loans.service.ts:71-77`) reads `BusinessBankAccount` where `isActive: true` — ~30 real seeded accounts (`backend/prisma/seed.ts:5183-5436`), unrelated to the shorter 7-item list from the client's POS Bank Transfer screenshot (see "Not in this scenario" below — those are two different data sources).
3. **The GL side already has a working bank-routing path to mirror.** For `BANK_TRANSFER`, `create()` resolves the credit leg via `resolveBankGlAccount(dto.bankAccountId)` (`employee-cash-loans.service.ts:214-216, 282-292`), which falls back through the bank's own `glAccountId` to `DEFAULT_CASH` via `posting.resolveAccount()`. This is the exact mechanism to reuse if Cash/Check should also route their credit leg through a selected bank account (see Gap 2 below).
4. **A reusable JE-reversal mechanism already exists**, built for other modules: `JournalPostingService.reverse(originalId, postedBy, tx)` (`backend/src/accounting/posting/posting.service.ts:520-561`) — flips every line's debit/credit, tags the new entry `REV-<original code>`, carries the original's `branchId` forward, and accepts an optional transaction client so it can be composed into a larger atomic write. This is the pattern Part 2 should call, not reinvent.
5. **The financing/schedule computation is already isolated and reusable.** `computeFinancing()` and `buildSchedule()` (`employee-cash-loans.service.ts:88-141`) are pure functions already used by both `create()` and the live-preview endpoint (`preview()`, line 146-173) — the same functions an edit path needs to recompute a loan's terms from new inputs.

## What's not done / gaps ❌⚠️

1. **Cash and Check never show the Bank / Cash Account field at all** — confirmed bug matching the client's report (`NewLoanForm.tsx:239`).
2. **Even if the field is opened up to Cash/Check, the GL posting logic won't use it.** `create()`'s `cashAccountId` resolution (`employee-cash-loans.service.ts:214-217`) unconditionally maps CASH and CHECK to `DEFAULT_CASH`, never consulting `bankAccountId` — so simply un-gating the UI field would let a cashier pick a bank that the journal entry then silently ignores. This needs an explicit decision (see Open Questions), not an assumption.
3. **No update/edit path exists anywhere for a submitted loan.** `EmployeeCashLoansController` (`backend/src/pos/employee-cash-loans/employee-cash-loans.controller.ts`) exposes only `GET employees`, `GET bank-accounts`, `GET preview`, `GET` (list), `GET :id`, and `POST` (create) — no `PATCH`/`PUT` anywhere. `LoanDetail.tsx` (`frontend/src/app/(app)/(dashboard)/pos/employee-cash-loans/[id]/_components/LoanDetail.tsx`) is read-only; its only action is "Print Voucher" (line 152-158). This is genuinely net-new surface area, not a small extension.
4. **`EmployeeCashLoanScheduleLine` is a separate child table** (`backend/prisma/schema.prisma:2255-2268`), written via `scheduleLines: { create: schedule }` inside `create()`'s own transaction (`employee-cash-loans.service.ts:274`) — an edit that changes principal/term/rate can't patch schedule lines in place; it has to delete and regenerate the whole set.
5. **`currentBalance` always equals `openingBalance` today** — nothing reduces it yet (Scenario 52's own still-open item: no payroll-deduction/repayment recognition exists). This means the "does an edit disturb an already-partially-recovered balance" question is currently moot in practice, but the update logic should still have an explicit answer for it (see Open Questions), since repayment tracking is known future work, not hypothetical.

## Closing the gaps — proposed parts

Each part gets its own e2e coverage and manual test steps, and stops for confirmation before the next begins (house convention — see Scenario 51/52).

### Part 1 — Bank / Cash Account field for Cash and Check disbursement

Remove the `disbursementMethod === 'BANK_TRANSFER'` gate on `NewLoanForm.tsx:239` so the field renders for all three methods. The DTO already accepts `bankAccountId` optionally for any method, so no DTO shape change is needed for visibility alone.

**Confirmed 2026-09-21**: selecting a bank account for CASH/CHECK redirects the GL credit leg to that bank's own account, same as Bank Transfer already does — `create()`'s `cashAccountId` resolution (`employee-cash-loans.service.ts:214-217`) drops the `disbursementMethod === 'BANK_TRANSFER'` condition and instead branches on whether `bankAccountId` is present at all: set → `resolveBankGlAccount(bankAccountId)`; unset → `DEFAULT_CASH`.

**Also confirmed**: the field is required for all three methods, not just Bank Transfer. `create()`'s existing conditional check (`employee-cash-loans.service.ts:186-190`, "`bankAccountId` required only for `BANK_TRANSFER`") simplifies to an unconditional "`bankAccountId` is required" — same change mirrored in `CreateEmployeeCashLoanDto` (currently `@IsOptional()`, becomes required) and `NewLoanForm.tsx`'s client-side `validate()` (currently only checks it under `BANK_TRANSFER`, line 100-103).

### Part 2 — Make a submitted loan editable, with automatic reverse-and-repost

New `PATCH /pos/employee-cash-loans/:id` + `EmployeeCashLoansService.update()`.

**Confirmed 2026-09-21**: not every edit touches the GL. `update()` diffs the incoming DTO against the current row first:

- If only `note` and/or `referenceNumber` changed, patch the row directly — no reversal, no new JE, no schedule regeneration.
- If any financially-relevant field changed (`principal`, `termMonths`, `interestRate`, `loanDate`, `firstDeductionDate`, `disbursementMethod`, `bankAccountId`), run the full reverse-and-repost path, wrapped in one `$transaction` mirroring `create()`'s own shape (`employee-cash-loans.service.ts:219-279`):
  1. Call `this.posting.reverse(loan.journalEntryId, updatedBy, tx)` — the existing mechanism at `posting.service.ts:520`, not a new one.
  2. Recompute financing via the existing `computeFinancing()`/`buildSchedule()`.
  3. Delete the loan's existing `EmployeeCashLoanScheduleLine` rows and recreate them from the new schedule (child table, no in-place patch — see Gap 4).
  4. Post a new JE the same way `create()` does, and update the loan row (all edited fields + `journalEntryId` pointing at the new JE). `openingBalance` and `currentBalance` both reset to the newly recomputed `totalReceivable` — confirmed 2026-09-21, whatever was already recovered against the old balance is not carried forward (moot today, since nothing reduces the balance yet, but locked in now for when repayment tracking lands).

**Also confirmed**: `employeeId` and `loanNumber` are editable too, same as every other field — no field is excluded from "all." `employeeId` changes go through the same real-`Employee` lookup `create()` already does (`employee-cash-loans.service.ts:180-184`); `loanNumber` changes need the same duplicate-key handling other tenant-managed unique names in this codebase use (e.g. `PAYMENT_METHOD_OPTION`'s `DUPLICATE_OPTION_NAME`, `payment-methods.service.ts:507-517`) — `loanNumber`'s `@unique` constraint (`schema.prisma:2202`) means a P2002 on update needs a friendly "loan number already in use" error, not a raw 500.

Frontend: an Edit affordance on `LoanDetail.tsx` (currently pure read-only) — most likely reusing `NewLoanForm.tsx`'s field layout, pre-filled from the existing loan (including Employee and Loan Number as editable fields, not just displayed), submitting to the new PATCH action.

## Not in this scenario

- **The POS checkout Bank Transfer dropdown/bank list** (BPI-Araneta, BPI-Central, BDO-Golden Field, BDO-Quezon, Metrobank, GCash-Panay, GCash-Negros). Settled as a Settings → Payment Methods data change for NIG's live tenant — no code, no deploy, and no change to the code's seed default for future tenants (see Decisions taken).
- **Automatic payroll deduction / repayment recognition against an Employee Cash Loan balance**, and **the interest-release batch** recognizing deferred interest as earned over time. Both already explicitly deferred by Scenario 52 and remain untouched here.
