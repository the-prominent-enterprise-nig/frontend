## Gaps found ❌

1. **No 2-01-260 Income Tax Payable** in the chart (the only account on the `Tax GL Map` sheet that is missing). The client's own posting file (row 11J) already needs it.
2. **WHT Payable has one mapping.** `2-01-241` (Rent) and `2-01-242` (Professional Fees) exist in the chart but nothing posts to them. There is also no mapping for VAT Payable (`2-01-220`) or Income Tax Payable.
3. **No tax code master.** `taxCode` is a free-text string with three vocabularies: `ARInvoice` (`VAT / NON_VAT / EXEMPT`), expenses (`NON_TAXABLE / INPUT_VAT` plus legacy aliases), and unconstrained on `APBill`, `APBillLine`, PO lines and `SupplierDebitMemoLine`. No effective dates, no tax type, no mapped GL, no ATC.
4. **Withholding is hardcoded.** `WithholdingType` is `none | pct_1`. The 0.01 is hardcoded in `ap-bills.service.ts:126`, `stock.service.ts:1428` and `:65`, and `manual-receiving-report.service.ts:39`. The workbook needs 1% goods, 2% services, 5% rent, 5% / 10% professional fees.
5. **No ATC on the supplier side.** `Supplier.alphanumericTaxCode` and `taxRate` are free-text and drive nothing; `APBill` has no ATC.
6. **Expenses cannot withhold.** `BusinessExpense` / `BusinessExpenseLine` have no withholding field, so rent paid through Expenses cannot carry the 5% EWT.
7. **Output VAT has one VATable treatment** and one all-or-nothing `isTaxExempt` toggle on the transaction. No zero-rated sale, no VAT-exempt vs out-of-scope split, no per-line classification. No government VAT withholding.
8. **Input VAT is 12% or none.** No capital-goods, import or exempt treatments, and no "PEZA / Government" supplier VAT status.
9. **No tax reports or closing routines.** None of: VAT Summary, Output VAT Detail, Input VAT Detail, EWT Payable Schedule, Tax Code Exception report, VAT/WHT GL reconciliation, VAT settlement routine, WHT remittance routine.
10. **No override controls.** No override-reason field, no restriction on who can change a tax code, no audit of it.
11. **Customer withholding posts when the 2307 arrives**, not at collection (the decision above reverses this; Part B).

### Part C — Tax code master

**Built 2026-10-10** (backend `feat/tax-setup-vat-wht`; frontend same branch name).

- **`TaxCode` table** (`prisma/migrations/20261010140000_scenario_69_tax_code_master`): one row per **version** of a code: `code`, `name`, `taxType` (`OUTPUT_VAT | INPUT_VAT | EWT_PAYABLE | CWT_RECEIVABLE | WTC | OTHER`), `ratePercent` (a percent — 12 means 12% — returned by the API as a number), `baseRule` (`GROSS | VAT_EXCLUSIVE | VAT_INCLUSIVE_EXTRACT | NET_OF_VAT | FIXED | VARIABLE`), `atc?`, `accountMappingKey?`, `description?`, `isDefault`, `requiresApproval`, `isActive`, `effectiveFrom`, `effectiveTo?`. Unique on (`code`, `effectiveFrom`). Global, like `Account` and `AccountMapping` — not per tenant.
- **Effective-dated, as decided.** A rate change is a new version with a later `effectiveFrom`; the previous open-ended version is closed the day before; versions never overlap and a version cannot change its code's tax type. `TaxCodesService.resolve(code, asOf)` returns the version in force on a date, which is what Parts D–G read to price a transaction by its own date. Dates are calendar dates; "today" turns over at Manila midnight.
- **Seeded by the migration, not by the seed script**, so every environment gets them on `prisma migrate deploy` (Railway runs it as the release command). **21 codes**: `VAT-OUT-12/GOV-12/0ZR/EXEMPT/OOS`, `VAT-IN-12/CAPEX/NONVAT/EXEMPT/OOS`, `EWT-NONE/GOODS-1/SERV-2/RENT-5/PROF-IND-5/PROF-IND-10`, `CWT-AR-NONE/GOODS-1/SERV-2/GOV-VAT-5/CUSTOM`. Rates are the workbook's, **provisional**. Every ATC is empty, and every row starts at `2000-01-01` so backdated entries still resolve. `VAT-OUT-GOV-12` and `CWT-AR-GOV-VAT-5` are seeded **inactive**. `VAT-IN-IMPORT` and `EWT-CARD-0.5` are left out, as decided. `EWT-GOODS-1` is the default EWT code, matching the 1% supplier default. A guard unit test checks the seed SQL against the workbook and checks every posting key is real and suits its tax type.
- **A code can only post to a posting key that suits its type** (`tax-code.constants.ts`): Output VAT → `OUTPUT_VAT`/`VAT_PAYABLE`; Input VAT → `INPUT_VAT`; EWT → `WHT_PAYABLE`/`WHT_PAYABLE_RENT`/`WHT_PAYABLE_PROFESSIONAL`; CWT → `WHT_RECEIVABLE`; Other → any. No key at all is allowed (zero-rated, exempt, none).
- **API** (`/tax-codes`): `GET` (one row per code as of a date, with the change already scheduled), `GET by-code/:code` (history), `GET resolve/:code?asOf=`, `GET :id`, `POST` (a new code, or a new version of an existing one), `PATCH :id` (name, ATC, posting key, flags; `isActive` applies to the whole code). The rate, base rule, type and dates are **not** editable in place. Every write goes to the accounting audit log.
- **Permissions** `accounting:tax-codes:read|create|update`: Business Owner (catch-all) and Accountant (the `accounting:*` wildcard); the Branch Manager's explicit accounting list leaves them out. Rows added to `prisma/seed.ts`; `scripts/backfill-tax-codes-permissions.ts` for databases already seeded.
- **Screens** (full pages, no modals): **Accounting → Tax Codes** (`/accounting/tax-codes`: list with type / search / "rates as of" / show-inactive filters), `/accounting/tax-codes/[code]` (version history, inline edit of a version, deactivate/reactivate), `/accounting/tax-codes/new` (a new code, or `?code=` for a new version). The list says plainly that the rates are provisional.
- **Tests**: 54 unit tests (date/version rules, create/revision/update rules against an in-memory Prisma, seed guard), 17 backend e2e (`test/scenario-69-tax-codes.e2e-spec.ts`), 5 Playwright (`e2e/tax-codes.spec.ts`, read-only).

**Not in this part (by design):** nothing reads a tax code yet. Suppliers, AP bills, expenses and POS still use their current logic until Parts D–G switch them over, so no posting changed.

### Part D — AP & receiving use tax codes

**Built 2026-10-10** (backend `feat/tax-setup-vat-wht`; frontend same branch name).

- **Supplier.** New `defaultWithholdingTaxCode` (default `EWT-GOODS-1`; migration `20261010150000_scenario_69_ap_withholding_tax_codes`, which also maps every supplier already set to "no withholding" to `EWT-NONE`). The older `none | pct_1` flag stays and is **kept in step by the service**: writing a code sets the flag (`EWT-NONE` ⇒ `none`, anything else ⇒ `pct_1`), and a client that still sends only the flag moves the code (`none` ⇒ `EWT-NONE`; `pct_1` keeps the supplier's own non-none code, else `EWT-GOODS-1`). Where the two disagree on read, **`none` wins** (`supplierEwtCode()`), as it always did. The code is validated against the master: it must exist, be an `EWT_PAYABLE` code, be in force and be active.
- **Rates come from the master, by the document's own date.** `TaxCodesService.resolveEwt(code, asOf)` replaces the hardcoded `0.01`s in `ap-bills.service.ts`, `stock.service.ts` and `manual-receiving-report.service.ts` (the `WITHHOLDING_RATES` goods/services constants are gone). The default comes to exactly what the flat 1% did (same rounding, to the centavo).
- **AP bill.** New `withholdingTaxCode` and `withholdingAtc` columns. The code is the one named on the bill, else the supplier's, resolved at the bill date. A typed withholding amount still wins over the computed one; the code is recorded either way. The ATC is copied from the code and stays **empty until the accountant supplies the list**: it is never invented. Editing an amount keeps the bill's own code (a rent bill is not swapped back to the supplier's goods rate); changing supplier takes the new supplier's code. **A code that has since been switched off never locks a bill that already carries it**: it is only refused as a fresh choice.
- **Posting.** The bill's WHT credit posts to **its code's account**: rent → `2-01-241`, professional fees → `2-01-242`, everything else → `2-01-240` (`JournalPostingService.resolveWhtPayableAccount`: the code's key if mapped, else the general `WHT_PAYABLE`).
- **Receiving.** Header-driven receipts (what Receive-against-PO sends, VAT-inclusive) withhold at `dto.withholdingTaxCode ?? the supplier's code` on the **net-of-VAT stock value**. Per-line receipts (Manual RR, Stock-side RR) withhold each line at the code its class names (`goods` ⇒ `EWT-GOODS-1`, `services` ⇒ `EWT-SERV-2`) on the **line's VAT-inclusive total**, exactly as before. The draft AP bill a receipt scaffolds carries the receipt's code (`null` when one receipt mixed goods and services, `EWT-NONE` when nothing was withheld). A receipt whose lines all use one posting key credits that key's account; a mix credits the general account.
- **Screens.** Supplier form: a "Default withholding" dropdown of the master's EWT codes with their rates (replaces the 1% / None toggle); supplier detail shows the code and ATC. AP bill form: "Withholding Tax Code" dropdown (blank = the supplier's default; choosing another code clears the stale amount so it is worked out again; read-only on a bill made from a receiving report). The bill document names the code and ATC on its withholding line. The receiving previews (Receive-against-PO totals, Create/Manual Receiving Report totals and line rows) read the master's rates through `GET /tax-codes/options` and fall back to the workbook's 1% / 2% / 5% / 10% only while it loads. Static "1%" / "2%" labels on a **posted** receipt were removed: the rate in the master can change, and a printed rate must never contradict the amount that was taken.
- **Permission.** `GET /tax-codes/options` is readable by any of `accounting:tax-codes:read`, `inventory:suppliers:read`, `accounting:ap-bills:read`, `inventory:receive:create`, so people who pick a code do not need the whole master.
- **Tests.** 27 backend e2e (`test/scenario-69-ap-withholding-codes.e2e-spec.ts`: supplier code and flag sync, picker permissions, bills at each code, rent → `2-01-241` with the entry still balancing, dated rates and the Manila-day boundary, a switched-off code, header / VAT-inclusive / per-line / mixed receipts), 70 backend unit suites / 1,169 tests, 4 Playwright (`e2e/ap-withholding-codes.spec.ts`).

**Not in this part, deliberately:**

- The supplier VAT-status field (`VAT / NON_VAT / EXEMPT / GOVERNMENT / PEZA`) is **moved to Part G**, where it sets the default input VAT code; it has nothing to do with withholding and shipping it alone would be a field nothing reads.
- References are by **code string**, not a foreign key (`defaultWithholdingTaxCode`, `withholdingTaxCode`), like every other tax-code reference, because a code has many dated versions.
- The workbook says the base is net of VAT. The **per-line receiving** base stays VAT-inclusive because the NIG accountant confirmed it on 2026-10-05; the header-driven and AP-bill bases are net of VAT. The two are NOT the same number for a VATable line: raise it with the accountant before go-live.
- `none | pct_1` is not removed yet: other readers still use it. Remove once nothing reads it.
- No per-receipt override of the code on the Receive-against-PO screen (the API accepts `withholdingTaxCode`); a different rate is chosen on the supplier or the bill. The override-with-reason rule belongs to Part I.

### Part E — Expenses can withhold

**Built 2026-10-10** (backend `feat/tax-setup-vat-wht`; frontend same branch name).

- **Per line.** `BusinessExpenseLine` gets `withholdingTaxCode` (a code string, like every tax code reference), `withholdingAtc` and `withholdingAmount`; `BusinessExpense` gets the sum in `withholdingAmount` (migration `20261010160000_scenario_69_expense_withholding`, additive: every existing row is "not withheld"). The DTO takes only the **code**: the amount is **derived and never accepted**, the same rule as the line's VAT. It is the code's rate **on the expense date** × the line **net of VAT** (the workbook's example: ₱56,000 with 12% VAT inside is withheld on ₱50,000, so 5% is ₱2,500). The code must be in force, active and an EWT code; `EWT-NONE` or blank means not withheld.
- **Refused where withholding means nothing** (400, nothing saved): a deduction (negative line), a Special Account line (an advance, a loan, a recovery), and a `PAYROLL` / `SALARIES_WAGES` entry (compensation, which an EWT code does not cover; withholding on compensation is still out of scope).
- **The payments total what leaves the bank.** What was withheld is owed to the BIR, so the payment rows must total **the expense total less its withholding** (₱53,500 for the example), not the total. The old rule and its message are unchanged for an expense that withholds nothing. A payments-only edit is held to the same figure.
- **Posting.** `record()` credits Withholding Tax Payable **per code**, to **the code's own account** (rent → `2-01-241`, professional fees → `2-01-242`, everything else → `2-01-240`), beside the cash credits, so the workbook's entry posts exactly: Dr Rent 50,000 / Dr Input VAT 6,000 / Cr WHT 2,500 / Cr Cash 53,500, and it balances. Void reverses it with the rest of the entry. A code switched off since a draft picked it never locks that draft (same rule as an AP bill): it is refused only as a fresh choice.
- **VAT vocabulary.** An expense line now also accepts the master's own names for its two treatments: `VAT-IN-12` = Input VAT, and `VAT-IN-NONVAT` / `VAT-IN-OOS` / `VAT-IN-EXEMPT` = non-taxable. The legacy spellings keep working, what is stored is still the code that was sent, and the rate is still the flat 12% (the master's VAT rates are read from Part G). `VAT-IN-CAPEX` is deliberately not mapped: it needs the project / asset id Part G collects. A seed guard test checks these codes exist at the rates the line assumes.
- **Voucher.** The document carries per-line code / ATC / amount and the header `withholdingAmount` and `netPayable`. The printed voucher shows **Amount / Less: withholding tax (EWT-RENT-5) / Net amount paid** when something was withheld, and is unchanged when nothing was.
- **Screens.** Expense form: a **Withholding** column (a dropdown of the master's EWT codes, shown with their rates, default "None"; the amount withheld is shown under it), offered for a **Supplier** payee and an **Other** payee that is not a payroll run; not for a Customer refund, an Employee reimbursement or a payroll run, and disabled on a deduction or an advance / loan line. The footer adds **Less: withholding tax** and **Net payable**, and a single payment follows the net payable. The detail screen shows the withholding per line and the net. `GET /tax-codes/options` is now also readable with `accounting:expense:create`.
- **Tests.** 22 unit tests (`expenses-withholding.spec.ts`) plus 6 constants tests and a seed-guard test (72 backend unit suites / 1,198 tests in all), 24 backend e2e (`test/scenario-69-expense-withholding.e2e-spec.ts`: the workbook entry, payments, accounts, mixed codes, refusals, edits, void, dated rates, a switched-off code, the voucher document, the picker permission), 4 Playwright (`e2e/expense-withholding.spec.ts`).

**Two bugs in the existing expense form, found and fixed here** (both made Part E's figures wrong, so they could not wait):

1. **Reopening a saved draft inflated it.** The form still read a line's amount as stored net of VAT, so a draft saved as ₱56,000 with Input VAT reopened as ₱62,000. It reopens as typed now; a Playwright test guards it.
2. **The form's VAT split could differ from the server's by a centavo.** It split the 12% out as `net = amount / 1.12`, `vat = 12% of net`; the server takes 12/112 of the amount. Checked over every amount from ₱0.01 to ₱5,000.00: they disagreed on 42,385 of 500,000 amounts, and the form's total missed the typed amount on 53,571. The form now uses the server's own derivation (0 disagreements), which matters more now that the payment is sized off these figures.

**Decided, not asked:**

- **No default from the supplier.** An expense line starts at "None" even for a supplier whose default is `EWT-GOODS-1`: unlike a bill or a receipt, an expense is paid at once, and defaulting would silently cut the cash paid on every supplier expense already being entered. Choosing the code is explicit; a missing one on a supplier expense is a candidate for the Part I exception report.
- **No typed withholding amount** on a line (derived only, like VAT). An override with a reason belongs to Part I.

**Not in this part:** the master-driven VAT _rate_ for expenses (Part G), withholding on compensation (out of scope), and the EWT schedule by supplier / ATC (Part H, which will read these columns).

### Part F — Output VAT classification

**Built 2026-10-10** (backend `feat/tax-setup-vat-wht`; frontend same branch name).

- **One class per sale or invoice, read off the master.** `PosTransaction` gets `outputVatCode` and `outputVatApprovedBy`; `ARInvoice` gets `outputVatCode`, `taxExemptionRef` and `outputVatApprovedBy` (migration `20261010170000_scenario_69_output_vat_classification`, additive; it back-fills the POS rows that already exist: exempt ⇒ `VAT-OUT-EXEMPT`, otherwise `VAT-OUT-12`). `TaxCodesService.resolveOutputVat` returns the code's rate, whether it is restricted, and the **VAT bucket** it is reported in (VATable / zero-rated / exempt / out of scope). A custom 0% output code has no bucket and is **refused rather than guessed at**: a wrong bucket is a wrong VAT return. Per-transaction, not per-item (decided earlier: the catalog carries no per-item tax).
- **POS sale.** `outputVatCode` defaults to `VAT-OUT-12`; `VAT-OUT-0ZR` and `VAT-OUT-EXEMPT` are the other two a counter sale can take (out of scope is for receipts that are not sales; the government code is an invoice's). The older `isTaxExempt` switch still works as shorthand for the exempt code; sending it with a **different** code is a 400. The sale now stores its split in three buckets: `vatableAmount`, `vatExemptAmount` and, for the first time, `zeroRatedAmount` (zero-rated is no longer folded into "exempt"; `isTaxExempt` is true only for the exempt class). **A restricted class (zero-rated, exempt) needs the certificate it rests on and a manager's approval**: the same server-verified override a large discount takes (`managerOverride` + `managerUserId`, the manager's `pos:transaction:override` re-checked on the server), and the approver is stored on the sale. **A refund inherits the original sale's class** whatever the register sent, and asks for no approval of its own: refunding VAT that was never charged (or not refunding VAT that was) would leave the books disagreeing with the sale they reverse. A class switched off since the sale does not stop its refund.
- **AR invoice.** `VAT-OUT-12`, the government code (once the accountant activates it), zero-rated and exempt. Out of scope is **not offered**: an invoice credits Sales revenue, and a receipt that is not a sale belongs on a balance-sheet or other-income account. The tax has to agree with the class: zero-rated / exempt carry none (400 otherwise), and a VATable invoice on a real amount carries some. Left out, a new invoice that carries VAT is `VAT-OUT-12` and one that carries none stays **unclassified** (a guess either way would be a wrong VAT return; the Part I exception report finds them). A restricted class needs `taxExemptionRef` and **a new permission, `accounting:ar-invoices:restricted-vat`** (Business Owner and Accountant by grant, Branch Manager through the `accounting:ar-invoices:*` wildcard it already holds, the same tier that holds the POS override); the saver is recorded as the approver. An edit keeps an approval that still stands (same code, same certificate) and **needs approving again when only the certificate changes**; an empty code takes the classification off; a code switched off since a draft picked it never locks that draft. Sending posts no Output VAT for a 0% class (the tax is 0, so the existing posting already leaves it out). The audit log snapshot now carries the class, the certificate and the approver.
- **The customer's own default.** `Customer.isTaxExempt` / `taxExemptionRef` ride along in the POS customer search and the invoice customer search; picking such a customer starts the sale (or the invoice) VAT-exempt with the certificate filled in. Only a default: it can be changed, and a restricted class still needs its approval.
- **Screens.** POS checkout: the "Tax Exempt" toggle is now a **VAT treatment** selector (VATable / Zero-rated / VAT-exempt); a restricted choice asks for the certificate and shows an amber "needs a manager's approval" prompt that reuses the checkout's manager PIN dialog (its slot is shared with the discount override, so one approval covers both); not offered on a table tab's sale, which already exists; refused offline (approval needs the network). Transaction detail shows the treatment, the certificate and the approver **by name**. ### Part G — Input VAT variants

**Built 2026-10-10** (backend `feat/tax-setup-vat-wht`; frontend same branch name).

- **A supplier has a VAT status.** `Supplier.vatStatus` = `VAT` (default) / `NON_VAT` / `EXEMPT` / `GOVERNMENT` / `PEZA` (migration `20261010180000_scenario_69_input_vat`, additive; it back-fills `NON_VAT` for every supplier whose older `defaultInputVat` flag was `none`). The status **sets the input VAT code a purchase starts on**: `VAT` → `VAT-IN-12`, `EXEMPT` → `VAT-IN-EXEMPT`, `NON_VAT` / `GOVERNMENT` / `PEZA` → `VAT-IN-NONVAT`. The older `none | pct_12` flag stays (receiving still reads it) and is **kept in step by the service**: a status write sets the flag; a flag-only write (an older client) reads `pct_12` as `VAT` and `none` as `NON_VAT` unless the supplier already holds another non-VAT status. The supplier-master import derives it (ATC `NON-VAT` → `NON_VAT`, rate `EXEMPT` → `EXEMPT`, otherwise `VAT`), and the ad-hoc source suppliers that stock receiving and manual receiving create are `NON_VAT`.
- **A purchase line carries an input VAT code.** `VAT-IN-12` (the default), `VAT-IN-CAPEX`, `VAT-IN-NONVAT`, `VAT-IN-EXEMPT`, `VAT-IN-OOS`; `VAT-IN-IMPORT` stays **un-seeded** (no evidence NIG imports directly). `TaxCodesService.resolveInputVat(code, asOf)` reads the rate off the master on the **bill date** and returns the **bucket** the amount is reported in (claimable / capital / non-VAT / exempt / out of scope, for Part H's Input VAT reports). It refuses a missing code, one that does not exist or is not in force that day, one that is not an input VAT code, one switched off, and **a custom 0% input code it has no bucket for** (refused rather than guessed at, as with the output side).
- **AP bill lines.** The line's tax is **derived from its code**: `taxOn(line total, the code's rate)`. A typed `taxAmount` is ignored when a master code is sent, and the header Input Tax is the sum of the lines. A line with **no code keeps the older behaviour** (the typed tax), so a header-only bill and an API caller that sends no code are unchanged. Rules, all checked on the server and again on update (an existing line is re-checked when the supplier is changed):
  - a **claimable code (`VAT-IN-12`, `VAT-IN-CAPEX`) is refused for a `NON_VAT` or `EXEMPT` supplier** with the line number and the way out (code it `VAT-IN-NONVAT` / `VAT-IN-EXEMPT`, or correct the supplier). `GOVERNMENT` and `PEZA` are allowed: they start unclaimed but a line whose invoice shows VAT can be switched to `VAT-IN-12`;
  - **`VAT-IN-CAPEX` needs a project / asset reference** (`projectAssetRef`) **and an asset account**: property, plant and equipment, intangibles or other non-current assets, and not a header account;
  - **`VAT-IN-OOS` needs an account** that is not a tax account (it is a deposit, advance, loan payment or other balance-sheet item);
  - a line may now name **its own account** (`accountId`); a line that does not posts to the bill's expense account as before.
- **Posting at receive.** One debit **per line that names an account** (a capital line's description reads `Capital purchase (<asset tag>): <bill>`, so the tag travels to the ledger), the rest of the net to the bill's expense account, **Input VAT = the sum of the lines' tax**, credit Accounts Payable for the total less withholding, and the withholding line. A non-VAT bill posts no Input VAT. Same entry, balanced, as before when no line names an account.
- **Expenses.** An expense line can be **`VAT-IN-CAPEX`** (shown as "Capital goods (Input VAT)"): it needs the project / asset and an asset account, claims the same 12/112 Input VAT inside the VAT-inclusive amount, and is refused on a Special-Account line (those are balance-sheet settlements). `VAT-IN-CAPEX` joins the master names an expense line already understood (Part E deliberately left it out until this part collected the asset id).
- **The master protects the flat rate.** Creating a new version of `VAT-OUT-12`, `VAT-OUT-GOV-12`, `VAT-IN-12` or `VAT-IN-CAPEX` at any rate **other than 12** is refused with "still taxed at a fixed 12% by POS, receiving and expenses… needs a code change first": those paths read `FLAT_VAT_RATE_PERCENT`, so a different rate in the master would be classified at one rate and posted at another. (The AP bill reads the master; making the other three read it is the separate change Part F already flagged.)
- **Screens.** Supplier form: a **VAT status** select with a line saying what it means and what purchases start as (also on the supplier profile; the older 12% / none toggle is gone). AP bill form: each line has an **input VAT code** select (the claimable options are greyed out for a non-VAT or exempt supplier, with a banner saying why) and a **VAT** column showing what the code works out; a capital or out-of-scope line opens a **"Posts to" row** with the account (only property / equipment accounts for a capital line) and, for a capital line, the project / asset; the header Input Tax is read-only and comes from the lines. **A line you have not coded follows the supplier's default**, including a line added before the supplier's status has loaded or under a different supplier. The bill page lists each line with its code, VAT, account and asset tag. Expense form: the capital option, the project / asset field and an account picker narrowed to asset accounts; the expense page shows the tag.
- **Tests.** 58 new backend unit tests in four new specs (`input-vat.spec.ts` 11, `ap-bills-input-vat.spec.ts` 34, `supplier-vat-status.spec.ts` 7, `expenses-input-vat.spec.ts` 6) plus the guard, `resolveInputVat` and seed tests added to the tax-code specs (78 suites / 1,317 tests in all; two report-export specs hit Jest's 5-second timeout under full-suite load and pass alone). 29 backend e2e (`test/scenario-69-input-vat.e2e-spec.ts`: derivation per code, the typed tax ignored, the legacy no-code path, the supplier rule, capital and out-of-scope rules, update, and the receive posting with the asset tag; a non-VAT bill posts no Input VAT). 6 Playwright (`e2e/input-vat-variants.spec.ts`: the supplier status select, the bill form's default / derived VAT / capital validation / non-VAT lock / government override, the expense capital line). A clean-HEAD comparison of 24 existing AP, expense, supplier and receiving e2e specs shows **no new failure** (the failures they already have are identical on both trees). Two older Part D / E role-gate tests asserted the Cashier could not read `/tax-codes/options`; Part F opened that list to the Cashier on purpose (the POS sale-class selector), so they now use the CRM Marketing Manager as the role with no reason to pick a code, and a Cashier-can-read test was added.

**Behaviour changes to know about:**

1. **An itemised AP bill now claims Input VAT.** Before this part the form sent no tax for a line, so a bill with lines carried none. A line now starts on the supplier's default code, so a bill from a VAT-registered supplier carries 12% Input VAT per line and posts it to Input VAT.
2. **A non-VAT or exempt supplier cannot be billed a claimable code** (400). A government or PEZA supplier can, but starts unclaimed.
3. **A new dated version of a flat-rate VAT code can only keep 12%** (see above).
4. **An AP bill's line tax is no longer typed**: with a master code on the line the server works it out.

**Decided, not asked:**

- **Government and PEZA suppliers start unclaimed** (`VAT-IN-NONVAT`) and may be switched to `VAT-IN-12` per line, because they may or may not charge VAT on a given invoice; the safe side of "avoid claiming input VAT without valid support".
- **Receiving is unchanged.** Goods receiving and manual RRs still tax at the flat 12% and are gated by the kept-in-step `defaultInputVat` flag; they take no per-line code yet.

**Not in this part:** the Input VAT reports that read the buckets, the VAT settlement and WHT remittance routines (Part H); the override reason when a user changes a defaulted code, and the exception report for missing codes (Part I); a per-line code on receiving reports.

### Part H — Tax reports & closing routines

**Built 2026-10-10** (backend `feat/tax-setup-vat-wht`; frontend same branch name).

- **The ledger decides every amount; the document says what it was for.** The reports read the POSTED lines on the tax accounts (Output VAT 2-01-210, Input VAT 1-01-370, VAT Payable 2-01-220, the three withholding payables 2-01-240 / 241 / 242 and Creditable WHT 1-01-360, found through their account mappings) **by the entry's date, the way the General Ledger and the Trial Balance read them**, so a report's total ties to the books by construction. The document behind each entry (POS sale, AR invoice / payment / credit memo, AP bill, expense, receiving report, supplier debit memo, or one of our own closing runs) is looked up per entry and only explains the amount: its code, its base, who it was with. An entry no document explains is **listed anyway** and flagged "No source document"; a document that disagrees with its entry is flagged "Document differs from ledger" with the difference, **never silently picked over the ledger**. Sales that post no VAT line (zero-rated, exempt, out of scope, an invoice nobody classified that charged no tax) have nothing in the ledger to find them by, so they come from their documents: the Output VAT Detail would not reconcile to the sales reports without them. Periods are Manila calendar days and cannot reach past today.
- **An installment sale is explained by its sale, not by its contract invoice.** It is booked as one AR contract entry that names the installment plan; the invoice holds the whole contract (financing markup included, `taxAmount` 0 by design), so the sale named by the entry's reference carries the class, the VATable base and the VAT, and it is found by that reference (the invoice that points back at the entry is the fallback, and an exempt or zero-rated installment sale is listed from its sale too, not as a "not classified" contract). Found on the live dev data: three real installment sales were listed as "No source document" before this; they now read as `POS sale (installment)` with their customer and invoice number, and their VAT ties to the ledger to the centavo.
- **Six reports**, one screen with six tabs (`/accounting/tax-reports`; API `GET /reports/tax/{vat-summary, output-vat, input-vat, ewt-schedule, cwt-schedule, reconciliation}` with an `/export` twin each), one period and one set of filters (branch; tax code where it means something; search by document / party / TIN; plus ATC, certificate status and project / asset where they apply):
  - **VAT Summary by Period**: one row per month: VATable, zero-rated, exempt and other sales, Output VAT, Input VAT claimable / capital / other, adjustments and the net, with what a settlement has already cleared to VAT Payable; and, on the unfiltered report only, the company's balances still in the accounts at the end of the period, with the button that settles them.
  - **Output VAT Detail**: every sale and invoice with its VAT class, base and VAT, the customer's TIN, the branch and the run that has cleared it.
  - **Input VAT Detail**: every purchase line that carries VAT with its code, class (claimable / capital / non-VAT / exempt / out of scope), base, project / asset tag and the supplier's TIN.
  - **EWT Payable Schedule** by supplier and ATC (the data for the 2307s NIG issues to suppliers): code, rate, the implied income payment (withheld ÷ rate), the account, and the run that has remitted it. **An ATC the books do not carry is said ("No ATC", with a count and an amount on top), not invented**: the list has to come from NIG's accountant. Remitted / outstanding are shown on the whole report only (a remittance pays the three accounts together, so a searched or filtered view shows dashes and says why).
  - **Creditable WHT Receivable Schedule**: each collection a customer withheld on, with the 2307 status (Not received, with days outstanding / Received, with the certificate number, ATC, tax period and amount) and a filter for the ones still to chase; it extends the Pending-2307 aging.
  - **VAT/WHT GL Reconciliation**: for each of the seven tax accounts, opening, debits, credits and movement, split into what documents explain, closing entries, entries no document explains and documents that differ, then the closing balance and Reconciled / Review; plus six checks (sales with no VAT class, purchases with no code, withholding with no ATC / no code, 2307s pending, credit memos against VATable invoices).
- **Excel**: every report exports the shared report workbook (the tables on screen, native PivotTables on the four detail and schedule reports, and a Parameters sheet recording the period, the filters, who and when), built from the same result the screen shows; each export is audit-logged (`report:export`).
- **Branch scope** (list **and** drill-down, the `transfers.service.ts` convention): a branch-tied user sees only rows of their own branch whatever filter they send; head-office postings (no branch) are not theirs; and company balances (opening / closing / unsettled / remitted) are hidden, because a balance is the company's, not a branch's. Reports use the existing `accounting:financial_report:read`.
- **Two closing routines**, each a posted, reversible journal entry (`sourceModule: 'TAX'`) made from a screen that shows the entry first:
  - **Settle VAT through a day** (`/accounting/tax-closing/vat/new`): clears the Output VAT and Input VAT the books hold at the end of that day into VAT Payable: Dr Output VAT / Cr Input VAT / Cr (owed to the BIR) or Dr (creditable) VAT Payable. It is **balance-based and cumulative**, so an entry dated in an earlier month but posted late is picked up by the next run; the entry is dated that day.
  - **Remit withholding tax** (`/accounting/tax-closing/wht/new`): Dr each withholding account for what it holds / Cr the chosen bank account's GL account for the total. Two dates, because they are two things: the day the remittance **covers** and the day the money **left** (which dates the entry), plus the BIR payment reference. An account that holds a debit (more paid than withheld) is left alone and said so.
  - Each run is a `TaxSettlement` (`VATS-YYYYMMDD-NNNN` / `WHTR-YYYYMMDD-NNNN`; migration `20261010190000_scenario_69_tax_settlements`, additive). The through-day only moves forward per kind (a day already settled is refused, naming the run); only **the newest run still in force** can be reversed, with a required reason, through `JournalPostingService.reverse()`, and the day can then be run again. The screens say why they cannot post: unmapped accounts, nothing to settle, already settled through that day, no bank account, a payment date before the day covered.
  - Company-level: new permissions `accounting:tax-closing:read | create | reverse` for **Business Owner and Accountant** (the Branch Manager does not hold them: a settlement clears the company's balance, not a branch's; a branch-tied user gets the standard 403).
- **Screens**: full pages, no dialogs. The Tax Closing list (where each kind stands, the runs, filters), the two forms, and the run page (what it cleared, the entry it posted, the reversal with its reason and entry, and the "Undo this run" section). The sidebar gains Tax Reports and Tax Closing beside Reports. The report rows show the run number that cleared them.

A 59-check real-browser walkthrough on the running dev stack (throwaway documents, a Branch Manager login, both routines posted, reversed and re-run through the screens, the Excel file opened) finished with **every table in the database at the row count it started with**.

**Behaviour changes to know about:**

1. **Two new sidebar entries** (Tax Reports, Tax Closing) and a new route family; nothing existing moved.
2. **A VAT settlement or WHT remittance is a journal entry with source `TAX`**, not a manual JE: it has its own number, reads as a run on its own page, and is reversed from that page. **The Journal Entries screen now refuses to reverse a `TAX` entry** (400, "Reverse the run from Tax Closing instead"), so a run can never say it is in force over an entry that has been undone.
3. **The Branch Manager can read the tax reports for their branch but cannot see or run the closing routines.**

**Decided, not asked:**

- **GL-first, document-second.** A report can never disagree with the General Ledger; where a document disagrees the row says so.
- **Closing is balance-based through a day**, not by period activity: it is what clears the accounts to zero, and a late-posted entry for an earlier month is not left behind. The reversal is dated the day it is made (not the original's day), so a balance read as of an earlier day stays cleared and the books show when the undo happened.
- **The remittance's bank line is not tagged to the bank account's own ledger.** It credits the bank account's GL account (`bank.glAccountId`, else the default cash account) but does not create a bank transaction: bank reconciliation of the BIR payment is another session's work in progress (bank-account GL tagging) and this part leaves it alone.
- **Credit memos post no Output VAT line** (the existing credit-memo posting never did), so a credit memo against a VATable invoice does not reduce Output VAT in the books. The reconciliation lists them with the VAT they imply, for the accountant to decide; correcting the posting is a separate change.
- **No product-category filter**: the class is per transaction (decided in Part F) and the catalog carries no per-item tax to filter by.
- **ATCs are not invented**: a row without one says so, and the EWT schedule says it is not ready for BIR filing until the list is in.

3. **Fixed on the way: editing a DRAFT AP bill through the form handed a non-default withholding code back to the supplier's.** The form sends the supplier with every save, and `update()` took a supplier being sent for the supplier changing, so a 5% rent bill edited for its description went back to the supplier's 1% goods code while keeping its 5% amount. Now only a _different_ supplier takes on another supplier's defaults; the same root cause would also have let a supplier whose VAT status changed later block unrelated edits of an old bill. Regression tests at all three levels (unit ×2, backend e2e, Playwright).
4. **A register sale's detail waits for the full transaction before it shows the change**: it opens from a list row that carries no names, and "Someone" would flash first.

**Decided, not asked:**

- **Override scope per module** as above, and **the Branch Manager holds it**: it is the same trust as approving a restricted VAT class (which the Branch Manager already does), and the plan has them reading the report for their branch.
- **An exempt customer rung up VATable is a reason, not a manager.** VATable is the ordinary case; the manager's approval exists to stop an unsupported exemption.
- **Drafts are not on the report; nor are imported receivables or installment contract invoices as "missing a class".** A draft is still being worked on, and the others are nothing a user can fix (Part H explains the installment ones by their sale). The first run against the real dev data listed 5,362 "No VAT class" rows for imported invoices that have no entry, which is what made this rule.
- **The checklist item is a tick with a live count, not automatic.** A zero count still wants someone to say they looked, and a non-zero one can be fine to leave (an override with its reason).
- **The report scans documents, not the ledger**: what it looks for is a decision somebody made, or did not, which the ledger does not record.

**Before it goes live:** apply migration `20261010200000_scenario_69_tax_overrides` (three additive `taxOverride` JSONB columns); run `scripts/backfill-tax-override-permission.ts` on every real database (Business Owner, Accountant, Branch Manager), since `prisma/seed.ts` is a destructive reseed and is not for a live one.

**Not in this part:** the BIR return forms and 2307 print-outs; an approval workflow for an override (this records and gates it, it does not queue it for someone else to sign off); overrides on expenses.

## Decisions on the remaining questions (assistant-recommended 2026-10-10; developer may override)

1. **Part C — effective-dated rates: YES.** `TaxCode.effectiveFrom/To`; resolution by transaction date. A BIR rate change then never rewrites history, and the workbook lists it as Must Have. It does partly reverse the earlier removal of the configurable `TaxRate` table; that table had no dating and no approval workflow, which is not what this is.
2. **Part F — no per-item VAT code.** The VAT code is chosen per transaction (default `VAT-OUT-12`), and defaulted from the customer: `Customer.isTaxExempt` → `VAT-OUT-EXEMPT`. Evidence: no item has any tax field today, the catalog is all standard-VATable goods and services, and the existing exempt mechanism is customer/transaction-driven. Revisit only if NIG says it sells zero-rated or exempt goods.
3. **ATC and rates — build without them.** `TaxCode.atc` is nullable and editable in the tax code settings screen. Rates are seeded from the workbook as provisional. Missing ATCs show up in the Tax Code Exception Report (Part I), and the BIR-facing schedules in Part H must not go live until the accountant fills them in. This blocks go-live only, not development of Parts A–G. **Still needed from NIG's accountant**: the ATC list, and confirmation of 1% / 2% / 5% / 10%.
4. **Deferred codes.**
   - **Government:** the Customer Master template has government customers (a school, a provincial government), so seed `VAT-OUT-GOV-12` and `CWT-AR-GOV-VAT-5` as **inactive**, add a customer-profile hook, and activate only after the accountant confirms the treatment.
